# 曲库页重构方案

改曲库页（首页）的渲染、筛选或搜索之前读这份文档。这次重构沿用现在的视觉样式，目标是首屏更快、代码更清楚、筛选和搜索更可靠。之前的首页改版（DESIGN-HOME.md）已无限期推迟，与这里无关。

后台歌曲列表（`SongListClient`）和曲库页共用一套搜索函数，放在最后一个阶段一起换掉。

**状态：讨论中。** 第二节的问题清单里，每条都标了状态：

- **已确认**：确实是问题，按本文方案改；
- **待讨论**：可能是有意的设计，改之前先讨论；
- **保留**：讨论后确定是有意的设计，不改（讨论后再把条目移到这一类，并写明理由）。

第九节汇总了所有待讨论的事项。

## 一、实测基线

2026-10-31 在本地跑生产构建，测 `/zh-CN`：

| 项目 | 原始大小 | gzip 后 |
|---|---|---|
| HTML | 165 KB | 29 KB |
| 其中内嵌的歌曲数据（360 首） | 约 135 KB | 约 27 KB |
| 首页加载的 JS（24 个文件，不含只有旧浏览器才加载的 polyfill） | 约 1160 KB | 约 380 KB |
| HTML 里渲染出来的歌曲卡片 | 0 张 | |

JS 里能认出来的几块（gzip 后）：React 与 Next 运行时约 120 KB，framer-motion 约 47 KB，Base UI 与 floating-ui 约 27 KB 以上，Fuse 约 12 KB；播放条的代码也在首页的包里。

还没测、改之前要补上的：线上首页的 Lighthouse 分数，以及 Cloudflare Web Analytics 里真实用户的 LCP（首屏最大内容绘制时间）和 INP（交互响应时间）。这是改完之后对比用的基线。

### 搜索原型实测

2026-11-01 用线上曲库的真实歌词跑了一个原型（脚本没有进仓库），在台式机上测：

| 项目 | 结果 |
|---|---|
| 有歌词的歌 | 342 首，14716 句，约 13.4 万字 |
| 新接口 `lyrics-lines` 的响应（简繁各一份，大小几乎相同） | 原始 424 KB，gzip 165 KB，brotli 136 KB |
| 对比：旧接口 `lyrics-index` | 原始 349 KB，gzip 170 KB，brotli 142 KB |
| 服务端把全部歌词逐句转成繁体 | 141 ms（只在 ISR 重新生成时发生） |
| 逐字繁转简表 `t2s` | 3530 个字，gzip 14.6 KB |
| `pinyin-match` 简体版 | gzip 约 20 KB（繁体版约 63 KB，用不到，见第六节第 6 条） |
| 解析 JSON、归一化、构建 `corpus`（一次做完） | 21–25 ms |
| 单次精确搜索 | 0.02–0.2 ms |
| 单次兜底搜索 | 0.1–0.6 ms |

结论：

- **新接口压缩后比旧接口还小一点。** 按句子拆开多了一些引号和逗号，但去掉了署名区和说明行，两相抵消。
- **搜索本身快到可以忽略**，不需要 Web Worker。
- **构建 `corpus` 是唯一要注意的一步。** 台式机上 20 多毫秒，换到中档手机上估计要慢 4 到 6 倍，即 100 毫秒上下，一次做完会让输入框顿一下，所以要分段做（第六节第 9 条）。手机上的实际耗时还要在阶段 0 测。
- **精确匹配解决了 S1。** 按 `useLyricsIndex.ts` 注释里的记录，Fuse 搜「不知道」命中 53 首，其中 50 首不含这三个字（这个数字是当时记下的，这次没有重跑 Fuse）；原型只搜出 3 首，4 处命中，全部确实含有这三个字。
- **兜底能找回记错的歌词。** 用真实歌词各改一个字（如「血染江三的画」「怎敌你眉间一点朱沙」）、删一个字，阈值 0.6 时都只找回了原来那一首，没有带出别的歌。样本还少，阈值仍要用评测集确定。
- **繁体输入可用。** 「揮揮手 連流淚都沉默」归一化之后和简体原句命中同一处。

## 二、问题清单

编号按类别：R 渲染，I 图片，X 交互，F 筛选，S 搜索，C 代码结构。讨论时直接引用编号。

### 渲染

- **R1 首页 HTML 里没有内容，用户先看到加载屏。**（待讨论）`MusicLibraryClient` 通过 nuqs 读地址栏参数，nuqs 内部用 `useSearchParams`；静态预渲染遇到它就退回最近的 Suspense 边界，HTML 里只剩 `<Loading />`。用户要等 JS 下载、执行、水合，再在客户端渲染出卡片，图片才开始下载。搜索引擎拿到的原始 HTML 也只有加载屏，Google 曾把卷首标语当作首页摘要，就是这个原因。
- **R2 首屏用不到的 JS 也一起加载。**（待讨论）
  - Base UI 与 floating-ui 只在打开筛选下拉、顶栏菜单时才用到；
  - 播放条 `PlayerBar` 在全站的 `GlobalPlayer` 里静态引入，没有在播放也会被加载；
  - Fuse（搜索重构后删除，见 S 类）。
- **R3 挂载时就为搜索做准备，不管用户搜不搜。**（已确认）挂载时为整个曲库建 Fuse 索引；挂载 1 秒后无条件下载全量歌词。大多数访客不搜索。

### 图片

- **I1 封面下载的尺寸远大于显示尺寸。**（已确认）`CoverArt` 写的是 `width={400}`，没有 `sizes`，按 Next 默认的尺寸档位会请求 640 px（1 倍屏）或 828 px（2 倍屏）的图。网格卡片显示约 300 px；列表视图的缩略图只有约 56 px，下载的却是同一张图。
- **I2 首屏封面没有优先加载。**（已确认）所有封面都是懒加载，首屏那几张也要排队。
- **I3 封面经过自己服务器上的图片优化器。**（待讨论）占服务器 CPU，缓存只有 1 小时（`minimumCacheTTL: 3600`）。`cover.hetu-music.com` 是自己的图床，可以在上传封面时直接生成几档尺寸，绕开优化器。没有实测过服务器负载。

### 交互

- **X1 结果每变一次，卡片都重播进场动画。**（保留）每张卡片有 700 ms 的上滑淡入，依次错开 40 ms；搜索、筛选时新出现的卡片会播，翻页时网格的 `key` 带页码，整块重建后整页重播。这是有意的设计，重构时要原样保留：拆组件、改渲染方式之后，以上几种情况都要照旧播放。
- **X2 卷首的歌曲总数随筛选结果变化，每次变化都有动画。**（保留）有意的设计，同 X1，重构时原样保留。
- **X3 点左上角标志会调用 `router.refresh()`，重新下载整页数据。**（待讨论）如果目的只是重置筛选并回到顶部，这一步可以去掉。
- **X4 点卡片进详情页之前没有预加载。**（待讨论）歌名链接设了 `prefetch={false}`，卡片点击走 `router.push`。可以在悬停或卡片进入视口时预加载。
- **X5 从详情页返回时恢复滚动位置会闪一下。**（待讨论）内容先设为透明，等数据就绪、滚回原位再显示。R1 改完之后，这套逻辑要重新看。
- **X6 搜索框每敲一个字都改写地址栏两次。**（待讨论）搜索词一次，页码重置为 1 又一次。外面还包了一层 `useSyncedQueryState` 和 nuqs 的状态互相同步。

### 筛选

- **F1 年份在地址栏里存的是滑块位置，不是年份。**（已确认）`?yearStart=2&yearEnd=5` 是年份列表里的序号。曲库一旦加入新年份的歌，所有序号错位，旧链接筛出来的是另一段年份。
- **F2 人名在地址栏里存的是当前页面的字形。**（已确认）繁体页的歌曲数据整套转成繁体（`toTraditionalSongList`），繁体页的链接发到简体页，名字对不上，筛选失效。反过来也一样。
- **F3 切换简繁会丢掉所有查询参数。**（待验证）从代码推断：`useLocaleSwitch` 的 `switchTo` 调用 `router.replace(pathname, { locale })`，而 next-intl 的 `pathname` 不含查询参数。要在浏览器里确认。
- **F4 「全选」「反选」的压缩写法会随曲库变化改变含义。**（已确认）`encodeFilterParam` 在选中超过一半时只记录没选的项（`!某人`），全选记成 `*`。曲库新增一个人名后，旧链接会自动把他也包括进去。名字以 `!` 开头时还会被误读成排除项。
- **F5 选项不随其他筛选条件变化，容易组合出零结果。**（待讨论）可以把会导致零结果的选项置灰。注意：带「」的选项旁边不显示计数，这是已定的规矩，这里不加数字。
- **F6 「未知」是年份滑轨的最后一格。**（待讨论）拖到最右端会把年份未知的歌也包含进来，界面上不容易看出来。

### 搜索

- **S1 模糊匹配的噪音太大。**（已确认）歌词用 Fuse.js 做字符级模糊匹配（`threshold: 0.35`，`ignoreLocation: true`），散落的几个字也算命中。`useLyricsIndex.ts` 的注释记着一个例子：搜「不知道」命中 53 首，其中 50 首不含这三个字。中文记错歌词，通常是同音字或少记、多记几个字，编辑距离描述不了。
- **S2 排序难以解释，歌词索引一到结果还会重排。**（已确认）歌词和题名、人名在同一次 Fuse 打分里比，歌词权重 0.15，整首拼成长字符串又被按长度降权。没有歌词时用的索引（`createFuseInstance`：`threshold: 0.4`，专辑 0.2）和有歌词时用的（`useLyricsIndex`：`threshold: 0.35`，专辑 0.15）参数不同，索引一到，已显示的结果整体重排。
- **S3 片段展示粗糙。**（已确认）`processLyricsForSearch` 把各句用空格拼成一行，片段常常跨句截断；不高亮命中的字；片段里不一定有用户搜的字。
- **S4 繁体页搜不好、显示不对。**（已确认）歌词索引只有简体，繁体页输入的繁体字不转简体，「夢」搜不到「梦」；片段只显示简体。题名、人名在繁体页上是繁体，用户输入简体又匹配不上。
- **S5 歌词索引到达会打断输入。**（已确认）挂载 1 秒后才拉全量歌词，用户已在打字时，结果会突然变一次。

### 代码结构

- **C1 `MusicLibraryClient` 有 621 行，整页都是客户端组件。**（已确认）状态、筛选的编码解码、工具栏、列表、分页都在一个文件里。不拆开，R1 就没法做：服务端能渲染的部分（卷首、工具栏骨架、默认的第一页列表）和依赖地址栏参数的部分混在一起。
- **C2 五个多选筛选的代码各复制了一遍。**（已确认）曲风、演唱、作词、作曲、编曲分散在 `useMusicLibraryState`（五组状态与设置函数）、`MusicLibraryClient`（五组编码解码）、`searchAndFilterSongs`（五段匹配）、`calculateFilterOptions`（五段选项统计）、`SongFilters`（十个属性）。再加一个筛选维度要改五六个文件。
- **C3 搜索和筛选捆在一个 10 个参数的函数里。**（已确认）`searchAndFilterSongs` 和 `filterSongs` 按参数位置传值，后台的 `useSongs` 只用搜索，也要传一串空数组。

## 三、渲染方案

### 1. 服务端渲染默认状态（R1，待讨论）

推荐的做法：

- 首页保持 ISR。服务端把「第一页、不带任何筛选和搜索」的列表直接渲染成 HTML。
- 客户端**水合时不读地址栏参数**，先按默认状态渲染，保证和服务端的 HTML 一致；挂载之后，如果地址栏带了参数，再按参数筛选一次。
- 读参数的方式要换掉：只要水合时调用了 `useSearchParams`，整块就会退回客户端渲染。可以用 `useSyncExternalStore` 自己读 `window.location`，服务端快照返回默认值；写地址栏继续用 `history.replaceState`。是否还保留 nuqs，实施时再定。
- 带参数的链接会先显示默认列表、再切到筛选结果。为了不闪，在 HTML 里放一小段内联脚本：检测到地址栏带了筛选或搜索参数时，先把列表区域隐藏，筛选完成后再显示。

卡片的进场动画（X1）是纯 CSS（`animate-in`），服务端渲染出来的卡片在 CSS 加载后就会播放，不用等水合。挂载后按地址栏参数重新筛选时，新的卡片再播一次，和现在「每次变化都播」的行为一致。代价是首屏卡片从透明开始，LCP 要等动画走完一部分才记到，会晚几百毫秒。动画既然保留，和基线对比 LCP 时要把这一点考虑进去。

不推荐的做法：服务端读查询参数，按参数渲染。每个请求都要在服务端渲染一次，ISR 失效，服务器和数据库的压力明显上升。

这一步依赖 C1 的拆分：卷首、工具栏骨架、列表的第一页要能脱离地址栏状态单独渲染。

### 2. 精简首屏 JS（R2，待讨论）

- 播放条：`GlobalPlayer` 改为在有曲目时才动态加载 `PlayerBar`（`next/dynamic`）。这一条和视觉无关，可以直接做。
- 筛选面板（`SongFilters`）只在展开时才用到，改为动态加载，Base UI 的下拉和 floating-ui 随之延后。
- framer-motion 不动：卷首的数字切换和简介切换都用它，这些动画要保留（X1、X2），而且卷首就在首屏，延后加载反而会让动画晚出现。

### 3. 三档加载时机（R2、R3）

「不在首屏路径上」不等于「等用户操作才加载」。延后的代码在页面空闲时就预加载好，用户第一次点搜索框或筛选按钮时，基本不需要再等。按三档安排：

| 档 | 什么时候加载 | 内容 |
|---|---|---|
| 一 | 首屏就有 | 列表、卷首、工具栏，包括搜索框和筛选按钮本身 |
| 二 | 页面空闲时预加载代码（`requestIdleCallback` 里调用 `import()`） | 搜索内核（含 `t2s` 表和 `pinyin-match`，gzip 合计约 37 KB）、筛选面板 `SongFilters` |
| 三 | 用户表现出要搜索时才拉数据 | 歌词索引 `lyrics-lines`（gzip 约 165 KB） |

- **第二档的代码万一还没到**（用户点得特别快），搜索框照样可以输入，结果晚一两百毫秒出来，不锁页面。筛选面板同理：点开时如果代码还没到，先显示面板的外框，下拉框随后出现。
- **地址栏带了搜索或筛选参数时，第二档改为挂载后立即加载**：解析地址栏里的人名要用搜索内核的 `normalize()`（第五节第 2 条）。这时列表本来就被内联脚本隐藏着（第三节第 1 条），等筛选完成再显示。
- **歌词数据不放进空闲预加载**：它比代码大得多，而大多数访客不搜索，手机流量下白白下载不划算。如果之后想更激进一些，可以在没开省流量模式（`navigator.connection.saveData`）时也空闲预加载。
- **第二次访问时三档都不用等**：代码在浏览器缓存里，歌词索引在 Service Worker 里（带版本号的地址，见第六节第 9 条）。

对比现在：挂载时就为整个曲库建 Fuse 索引，和首屏渲染、水合抢主线程；挂载 1 秒后无条件下载全量歌词，和首屏封面抢带宽。每个访客都要承担这两笔开销，不管搜不搜。

## 四、图片方案

- **I1**：`CoverArt` 加上 `sizes`，按网格的列数和列表缩略图的实际宽度写。列表视图和网格视图传不同的值。
- **I2**：网格视图首屏的那一行（宽屏 4 张，窄屏 1 到 2 张）设 `priority`（或 `fetchPriority="high"`），其余继续懒加载。只有 R1 完成、首屏卡片出现在 HTML 里之后，这一条的效果才完整。
- **I3**（待讨论）：上传封面时在图床上生成 3 档尺寸（比如 96、384、768 px），`CoverArt` 用自定义 `loader` 直接指向图床，不再经过 Next 的图片优化器。这需要改上传流程（`service-upload.ts`）并给已有封面补生成，工作量单独评估。

## 五、筛选方案

### 1. 用一份配置描述筛选维度（C2）

```ts
const FACETS = [
  { key: "genre",    param: "genre",    values: (s) => s.genre,    order: GENRE_ORDER },
  { key: "artist",   param: "artist",   values: (s) => s.artist },
  { key: "lyricist", param: "lyricist", values: (s) => s.lyricist },
  { key: "composer", param: "composer", values: (s) => s.composer },
  { key: "arranger", param: "arranger", values: (s) => s.arranger },
] as const;
```

地址栏状态、选项统计、匹配和筛选界面，都改成由这份配置驱动的通用实现。同一维度内是「或」，维度之间是「且」，和现在一致。以后要加基调、意象母题这类筛选时，配置还要能表达「值本身有层级」（如母题属于某个分类），到时再扩展，现在不提前设计。

类型标签（`type`）是单选，年份是区间，这两个保持各自的写法，但同样从配置读取，不再单独散落。

### 2. 地址栏格式（F1、F2、F4）

- 年份存实际年份：`?year=2015-2020`；单独一年写 `?year=2018`；「未知」用 `&yearUnknown=1` 表示（F6 讨论的结果可能会改变这一条）。
- 人名、曲风存**归一化后的简体**，归一化函数复用搜索内核的 `normalize()`（第六节第 2 条）。简繁两种页面打开同一个链接，结果一致。
- 去掉 `*` 和 `!` 的写法，选了什么就存什么。
- **旧格式兼容一个版本**：读到 `yearStart`、`yearEnd`、`*`、`!` 时，按当时的选项列表转换一次，再用新格式改写地址栏。之后删除兼容代码。

### 3. 切换简繁时保留查询参数（F3）

在浏览器里确认 F3 之后，`switchTo` 改为把当前的查询参数一起带上。改动很小，可以随时单独做。

### 4. 搜索与筛选拆开（C3）

- `filterSongs(songs, facetState)`：只负责筛选，纯函数；
- 搜索的分档排序（第六节第 3 条）：只负责搜索，纯函数；
- 曲库页先筛选、再在筛选结果里搜索排序；后台只用搜索。

## 六、搜索方案

搜索的目标：

- 搜得到的都确实含有搜索词；搜不到时才放宽条件，放宽的结果排在后面并有标记。
- 排序规则写死、可以解释、可以测试。
- 片段显示命中的那一整句，高亮命中的字。
- 简繁两种页面都能用任意一种字形搜索，片段按页面字形显示。
- 歌词索引到达时只在末尾追加结果，不重排已经显示的结果。

这次不做：同音字匹配（拼音只用于题名和人名）；服务端全文检索（以现在的曲库规模，客户端足够）；播放器歌词和反馈表单选歌在繁体页显示简体的问题（另起 PR）；搜索结果的界面改版（第一版只改片段的内容和高亮）。

### 1. 歌词索引：新接口，按句子存

新增 `GET /api/public/songs/lyrics-lines?locale=`，返回：

```ts
type LyricsLinesEntry = {
  id: number;
  lines: string[]; // 按页面字形，已去掉署名区与说明行
};
```

- **句子切分复用 `buildFolio`**（`utils-folio.ts`），传入歌名和 `lyricsStart`。它已经能去掉开头的「作词：」之类的署名区和说明行，切出来的句号也和详情页一致，以后做「点片段跳到那一句」不用再对齐。
- **繁体版在服务端逐句转换**（`toTraditional`，和详情页同一个转换器），保证句数不变。
- **用新路径，而不是改旧接口的格式。** 旧接口 `lyrics-index` 在 CDN、Service Worker（`NetworkFirst`，网络超过 5 秒或离线时返回旧缓存）和 ISR 三处都有缓存，原地改格式的话，部署后一段时间内客户端会拿到旧格式。旧接口保留一个版本，确认没有请求后再删。
- 不带时间戳。以后要做「从这句开始听」，再加一个和 `lines` 等长的 `times` 数组。

### 2. 归一化

匹配之前，搜索词和被搜的文本都做同一套归一化：

1. 去掉标点、空格和各类符号；
2. 全角转半角，拉丁字母转小写；
3. **繁体逐字转简体**，一个字只换成一个字，所以长度不变。

每段文本归一化时，同时记下「归一化后第 i 个字 → 原文第几个字」的位置表，高亮时用它把命中区间映射回原文。

逐字转换表由脚本从 opencc-js 的字典生成（`scripts/gen-t2s-table.ts` → `src/lib/search/t2s.json`，生成后提交），客户端只打包这张表，不打包 opencc-js。生成方法：取 `TSCharacters`（繁→简）里一个字对一个字的条目，再把 `TWVariantsRev`（台湾异体字→标准繁体）接到前面。原型生成的表有 3530 个字，gzip 后 14.6 KB。

已知的局限：繁体版按词转换（opencc 的 `twp` 方案，比如「软件」→「軟體」），逐字转回去得到「软体」，所以在繁体页用简体输入「软件」搜不到。古风歌词里这类现代词汇很少。

### 3. 匹配与排序

一首歌按它**命中的最好那一档**排序，档位越靠前排得越前：

| 档 | 条件（都在归一化之后比较） |
|---|---|
| 1 | 题名完全相同 |
| 2 | 题名以搜索词开头 |
| 3 | 题名包含搜索词 |
| 4 | 题名拼音命中（见第 6 条） |
| 5 | 人名完全相同：演唱、作词、作曲、编曲，以及别署 `creditAliases` |
| 6 | 人名包含搜索词，或人名拼音命中 |
| 7 | 专辑包含搜索词 |
| 8 | 歌词有一整句和搜索词完全相同 |
| 9 | 歌词有一句包含搜索词 |
| 10 | 兜底命中（见第 5 条），只对歌词 |

- **档内排序**：歌词档按命中的句数从多到少，再按第一处命中的位置从前到后；其余情况保持曲库原有顺序（稳定排序）。
- **歌词各档都排在元数据各档之后**，所以歌词索引到达时只会在末尾追加结果（对应 S5）。
- **单字搜索**只匹配第 1 到第 7 档，不搜歌词，否则几乎每首歌都会命中。

### 4. 多个词

搜索词按空格分开时，每个词都要在这首歌的某个字段里命中（不必是同一个字段或同一句）。这首歌的档位，取各个词各自最好档位中**最差**的那一个。片段优先选同时包含多个词的句子。

### 5. 兜底：搜不到时再放宽

只在**精确命中的歌少于 3 首**、并且歌词索引已经到达时启用：

1. 把归一化后的搜索词切成相邻两字的片段（bigram），比如「倾尽天夏」切成「倾尽」「尽天」「天夏」；
2. 逐句计算覆盖率：这一句包含了其中多少个片段；
3. 覆盖率达到阈值、并且至少命中 2 个片段的句子算兜底命中，每首歌取覆盖率最高的那一句。

阈值先定 0.6，阶段 0 用评测集调整。三个字的搜索词只有两个片段，错一个字就到不了阈值，这种情况接受搜不到。兜底结果在界面上要和精确命中区分开。

### 6. 拼音

新增依赖 **pinyin-match**，只用于题名、人名和别署：

- 只在搜索词全是拉丁字母、并且至少 2 个字母时启用；
- 支持全拼（`qingjin`）和首字母（`qjtx`）；
- 对归一化后的文本做拼音匹配，命中位置经位置表映射回原文，用于高亮。
- **只引入简体版**（`pinyin-match` 的默认入口，gzip 约 20 KB）。归一化已经把繁体转成简体，用不到它的繁体版（`pinyin-match/es/traditional`，gzip 约 63 KB）。

不用于歌词：歌词长、同音字多，噪音太大。

### 7. 片段

- 显示命中的那一整句，高亮命中的字；
- 一首歌命中多句时，显示最靠前的一句，后面标「等 N 处」；
- 句子太长时以命中位置为中心截取，两头加省略号；
- 繁体页显示繁体原文。

只有在歌词档命中的歌才显示片段，和现在一致。

### 8. 加载时机

整体安排见第三节第 3 条的三档加载。具体到搜索：

- 搜索内核的代码在页面空闲时预加载（第二档）。
- 歌词索引在搜索框获得焦点时开始拉（第三档）；地址栏里已带搜索词时，挂载后立即拉。不再固定延迟 1 秒。
- 从点进搜索框到敲完第一个词，通常已经过去半秒以上，再加上 300 毫秒的防抖，这段时间里题名、人名的结果先出来。
- 索引到达之前只匹配第 1 到第 7 档，结果末尾标一行「歌词检索准备中」；到达后追加歌词各档的结果，已经显示的结果不重排。
- `corpus` 在索引到达时分段构建一次（第 9 条），之后每次按键只做查找。防抖沿用 300 毫秒。

### 9. 客户端的数据结构与缓存

**下载格式不做专门设计。** 副歌这类重复文本会被 brotli/gzip 压掉，一两 MB 的 `JSON.parse` 也只要十几毫秒。阶段 0 量出来的大小如果远超预期，再回头考虑。

**内存结构：一整串文本，不存句子数组。**

```ts
type LyricsCorpus = {
  corpus: string;          // 全部句子归一化后拼接，句间用 \u0001 隔开
  lineStart: Int32Array;   // 每句在 corpus 里的起点
  lineSong: Int32Array;    // 每句属于哪首歌（歌曲 id）
  lines: string[];         // 原文，按句号索引，显示片段时用
};
```

- **分段构建，不一次做完。** 原型在台式机上一次构建要 21–25 ms，中档手机估计 100 ms 上下，用户正在打字时会顿一下。改为每处理四十首左右的歌就把主线程让出来一次（`scheduler.yield()`，不支持的浏览器用 `setTimeout(0)`），每段在手机上控制在十几毫秒以内。分段构建期间到来的搜索，先只查元数据各档，构建完成后再补上歌词结果。如果阶段 0 实测分段之后仍然明显，再把构建挪进 Web Worker。
- 每个搜索词只在 `corpus` 上反复调用 `indexOf`，再用二分查找定位到句子和歌，不遍历上万个短字符串，低端手机上省内存。原型里单次搜索 0.02–0.6 ms，不需要 Web Worker。
- 分隔符保证命中不会跨句；归一化去掉了所有符号，`\u0001` 不会出现在正文里。
- 位置表**按需计算**：只给当前页要显示片段的那十几句算。
- 兜底匹配也在 `corpus` 上做，只在精确命中太少时执行。

**缓存：带版本号的地址。**

- 首页的页面数据里带一个歌词版本号：全部歌曲最近一次更新时间的短哈希。
- 客户端请求 `lyrics-lines?locale=…&v=<版本号>`。地址不变，数据就按「不会再变」缓存：Service Worker 对这个接口用 `CacheFirst`，CDN 设长缓存（`immutable`）。
- 歌词更新后版本号随之变化，客户端自然请求新地址；旧地址的缓存交给 Service Worker 的过期清理。
- 用户第二次打开曲库页时，索引直接从本地读出，「歌词检索准备中」只在第一次出现。
- **接口忽略 `v`，始终返回当前数据。** 首页是 ISR 页面，带出去的版本号可能比接口实际的数据新或旧；`v` 只用来区分缓存地址，下一次版本号变化时自然纠正。也因此，`server-revalidate.ts` 不必再清这个接口的 CDN 缓存。

### 10. 代码结构

```
src/lib/search/
  normalize.ts     归一化与位置表（筛选的地址栏格式也用它）
  t2s.json         逐字繁转简表（脚本生成）
  pinyin.ts        对 pinyin-match 的封装
  corpus.ts        构建 LyricsCorpus
  rank.ts          分档匹配、多词、兜底、排序
  snippet.ts       片段截取与高亮区间
  eval-cases.ts    评测集
src/hooks/library/
  useLyricsLines.ts  拉取索引，构建 corpus（取代 useLyricsIndex）
```

筛选：
