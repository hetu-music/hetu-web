# 曲库页重构方案

改曲库页（首页）的渲染、筛选或搜索之前读这份文档。这次重构沿用现在的视觉样式，目标是首屏更快、代码更清楚、筛选和搜索更可靠。之前的首页改版（DESIGN-HOME.md）已无限期推迟，与这里无关。

文档按实施阶段组织，一个阶段一节。每节写明：要解决哪些问题（编号见附录 A）、怎么做、步骤、验收，以及**开工前要定的事**。开工前要定的事没定下来，这个阶段就不动手。

## 贯穿各阶段的约束

- **视觉样式不变。** 必须改动界面的地方（如阶段 5 的片段高亮），按 DESIGN.md 来。
- **动画原样保留（X1、X2）。** 搜索、筛选时新出现的卡片播进场动画；翻页时网格的 `key` 带页码，整页重播；卷首的歌曲总数每次变化都有动画。这些是有意的设计。拆组件、改渲染方式之后，以上几种情况都要照旧播放。framer-motion 因此保留。
- **依赖变化**：不新增搜索库（拼音搜索不做，不引入 `pinyin-match`）；删除 `fuse.js`（阶段 6）；`opencc-js` 仍然只在服务端用。

## 背景：实测数据

### 首页基线

2026-10-31 在本地跑生产构建，测 `/zh-CN`：

| 项目 | 原始大小 | gzip 后 |
|---|---|---|
| HTML | 165 KB | 29 KB |
| 其中内嵌的歌曲数据（360 首） | 约 135 KB | 约 27 KB |
| 首页加载的 JS（24 个文件，不含只有旧浏览器才加载的 polyfill） | 约 1160 KB | 约 380 KB |
| HTML 里渲染出来的歌曲卡片 | 0 张 | |

JS 里能认出来的几块（gzip 后）：React 与 Next 运行时约 120 KB，framer-motion 约 47 KB，Base UI 与 floating-ui 约 27 KB 以上，Fuse 约 12 KB；播放条的代码也在首页的包里。

### 线上首页 Lighthouse

2026-11-01 在本机对 `https://www.hetu-music.com/zh-CN` 跑 Lighthouse 13.6（只测性能）。手机是默认的模拟条件：慢速 4G（约 1.6 Mbps，往返 150 ms），CPU 降速 4 倍。

| 条件 | 分数 | FCP | LCP | TBT | CLS | 页面总传输量 |
|---|---|---|---|---|---|---|
| 手机（3 次） | 52 / 48 / 42 | 2.0–2.3 s | 19.7–20.5 s | 0.76–1.72 s | 0 | 4.0 MB |
| 桌面（1 次） | 63 | 1.7 s | 4.7 s | 0.11 s | 0 | 4.4 MB |

FCP 是首次绘制出内容的时间，LCP 是首屏最大内容绘制完成的时间，TBT 是主线程被长任务占住的总时长，CLS 是布局跳动。

**页面传输量的构成**（手机第 1 次）：

| 类型 | 数量 | 传输量 |
|---|---|---|
| **字体** | 65 个 | **2814 KB** |
| 其中 next/font 加载的思源宋体、思源黑体（`Noto_Serif_SC`、`Noto_Sans_SC`） | 40 个 | 2570 KB |
| 其中楷体（`/fonts/kaiti`） | 15 个 | 127 KB |
| 其中 `/fonts/keben` | 10 个 | 117 KB |
| JS | 27 个 | 425 KB |
| CSS（其中三份字体的 `@font-face` 声明 `result.css` 共约 170 KB） | 6 个 | 272 KB |
| 图片（首屏封面） | 4 个 | 326 KB |
| 接口请求（其中歌词索引 171 KB） | 9 个 | 194 KB |

**LCP 元素是第一张卡片的封面**（`<img loading="lazy">`，没有 `fetchpriority`），请求的是 828 px 宽的图，显示宽度 364 px。本机实际网络下（未模拟降速）LCP 的分解：首字节 0.4 s，开始加载封面前的等待 1.1 s，封面下载 1.1 s，渲染 0.07 s。

结论：

- **字体是最大的负担**：占页面传输量的七成。慢速网络下，两千多 KB 的字体和首屏封面抢带宽，这是手机 LCP 被模拟到 20 秒的主要原因。这一项之前没有列进问题清单，现在补为 T1。
- 模拟降速下的 20 秒偏悲观，但改前改后用同样条件对比，趋势是可信的。
- I1（封面尺寸）、I2（首屏封面懒加载）、R3（挂载后无条件下载歌词索引，171 KB）都在实测里得到了印证。
- 结果和测试所在的网络位置有关，改完之后要在同一台机器、同样的条件下重测对比。

### 搜索原型

2026-11-01 用线上曲库的真实歌词跑了一个原型（脚本没有进仓库），在台式机上测：

| 项目 | 结果 |
|---|---|
| 有歌词的歌 | 342 首，14716 句，约 13.4 万字 |
| 新接口 `lyrics-lines` 的响应（简繁各一份，大小几乎相同） | 原始 424 KB，gzip 165 KB，brotli 136 KB |
| 对比：旧接口 `lyrics-index` | 原始 349 KB，gzip 170 KB，brotli 142 KB |
| 服务端把全部歌词逐句转成繁体 | 141 ms（只在 ISR 重新生成时发生） |
| 逐字繁转简表 `t2s` | 3009 个字，gzip 13.0 KB（原型 3530 个字，含无效条目，见阶段 2） |
| 解析 JSON、归一化、构建 `corpus`（一次做完） | 21–25 ms |
| 单次精确搜索 | 0.02–0.2 ms |
| 单次兜底搜索 | 0.1–0.6 ms |

结论：

- **新接口压缩后比旧接口还小一点。** 按句子拆开多了一些引号和逗号，但去掉了署名区和说明行，两相抵消。
- **搜索本身快到可以忽略**，不需要 Web Worker。
- **构建 `corpus` 是唯一要注意的一步。** 台式机上 20 多毫秒，中档手机估计慢 4 到 6 倍，即 100 毫秒上下，一次做完会让输入框顿一下，所以要分段做（阶段 2）。手机上的实际耗时还没测。
- **精确匹配解决了 S1。** 按 `useLyricsIndex.ts` 注释里的记录，Fuse 搜「不知道」命中 53 首，其中 50 首不含这三个字（当时记下的数字，这次没有重跑 Fuse）；原型只搜出 3 首，4 处命中，全部确实含有这三个字。
- **兜底能找回记错的歌词。** 用真实歌词各改一个字（如「血染江三的画」「怎敌你眉间一点朱沙」）、删一个字，阈值 0.6 时都只找回了原来那一首，没有带出别的歌。样本还少，阈值仍要用评测集确定。
- **繁体输入可用。** 「揮揮手 連流淚都沉默」归一化之后和简体原句命中同一处。

## 阶段 1：独立的小改动

**解决**：I1、I2、R2（播放条部分）、F3、T1。X3、X4 讨论后保留现状。

**状态**：已提交；上线后在线上重测 Lighthouse（I1、I2 的效果本地测不出）。实测见本节末尾。

### I1 封面尺寸

`CoverArt` 的 `sizes` 改为必填，每个调用处写明封面实际显示的宽度：

- 网格（`GridCard`）：按栅格算，宽屏 284px，lg 三列、sm 两列按视口宽度算；
- 列表（`ListRow`）：`64px`；

**窄屏一列时故意少报四分之一。** 手机多是 2.6–3 倍屏，照实写会去要 1080–1200px 的图；而近年的封面原图多在 1280px 以上（抽样 16 张：一半不超过 640px，新的多在 1280–2126px），真会给这么大，比原来（不写 `sizes` 时最多 828px）还重。少报之后约等于按 2 倍屏取图，3 倍屏上与原来同为 828px。

### I2 首屏封面优先加载

按 Next 16 的文档，`priority` 已废弃；首屏哪张是 LCP 随视口而变时，用 `loading="eager"` / `fetchPriority="high"`，不用 `preload`。

- 网格第一张：立即加载，高优先级；
- 网格第 2–4 张（宽屏首行）：立即加载，优先级照常；
- 列表前 8 行：立即加载（缩略图只有几 KB）；
- 其余继续懒加载。

阶段 4 之前首屏卡片还不在 HTML 里，要等水合后渲染出来才开始下载；阶段 4 之后再检查一次。

### R2 播放条按需加载

`GlobalPlayer` 用 `next/dynamic` 加载 `PlayerBar`，有曲目时才下载。第一次点播放时条子晚出现一两百毫秒，声音不受影响（播放由 player-store 负责）。`PlayerBar.test.tsx` 里把 `next/dynamic` 换成同步的真组件，测试照旧。

实测：播放条和队列面板的代码（原首屏里约 8.6 KB）已不在首屏的包里。但首屏 JS 总量几乎没变（381 KB → 379 KB）：播放条用到的 Base UI 等库，首屏别的组件也在用，照样要加载。真正减 JS 要等阶段 4 把筛选面板延后。

### F3 切换简繁时保留查询参数

在无头 Chrome 里确认：从 `/zh-CN?q=天下&type=原创` 切到繁体，原来变成 `/zh-TW`，搜索框清空。

`useLocaleSwitch` 的 `switchTo` 改为点击时从地址栏读查询参数和锚点，一起带上。不在渲染时读：这些参数由 nuqs 浅更新，不经过路由，渲染时拿到的可能已经过时；也不用 `useSearchParams`，那会让顶栏所在的整块退回客户端渲染（R1）。修改后切到繁体是 `/zh-TW?q=天下&type=原创`，搜索框保留。

阶段 3 会改地址栏里人名的存法，在那之前，切换简繁后人名筛选仍然对不上（F2）。

### T1 字体：先用系统字体，首屏封面到了再换上思源

采用讨论中的做法 B，思源宋体和思源黑体都这样处理。字形不变，只是换上的时机晚一点；换上之前显示系统字体。

- `globals.css` 新增工具类 `cjk-deferred`：在这一层重写 `--font-sans`、`--font-serif`，去掉 `--font-body-sc`、`--font-heading-sc`，并重设 `font-family`。要重写整个字体栈，是因为这两个变量在 `:root` 上就已代入 `--font-sans` 等，只在下层改它们不生效；正文的字体是从 `body` 继承的，所以要在本层重设一次。
- `useDeferredCjkFonts`：曲库根容器先带上 `cjk-deferred`；网格视图等第一张封面加载完（或失败），列表视图、没有结果时等页面加载完，最多等 4 秒，然后去掉。去掉之后浏览器才去下载思源的分片。一旦换上就不再改回。
- 曲库渲染出来之前就在页面上的两处也用系统字体：`page.tsx` 里只给读屏软件看的站名 `<h1>`，以及加载屏外面包一层 `cjk-deferred`。只影响首页加载屏上那行「加载中」的字体。
- 范围只在曲库页。详情页等其他页面不变。

实测（生产构建，无头 Chrome，不用缓存）：第一张封面加载完之前，只有 Inter 和 Playfair 两个拉丁字母的小分片在下载；思源的分片全部在封面之后才开始。

开发模式下（`next dev`）首页是流式渲染，先显示 `(public)/loading.tsx` 的加载屏，那一屏不在 `cjk-deferred` 里，会提前拉 3 个思源宋体的分片；生产构建的静态页里没有这一屏，不受影响。

### 本地对比

2026-11-01 在同一台机器上，把改动前（当前提交，放在临时 worktree 里构建）和改动后的生产构建各起一个服务，交替各跑 3 次 Lighthouse 手机模式：

| | 分数 | FCP | LCP | TBT | Lighthouse 计入的传输量 | 其中字体 |
|---|---|---|---|---|---|---|
| 改动前 | 49 / 54 / 53 | 1.5 s | 24.8–24.9 s | 0.68–0.78 s | 4175 KB | 2882 KB |
| 改动后 | 55 / 53 / 55 | 1.5 s | 9.96–10.07 s | 0.77–0.92 s | 1161 KB | 335 KB |

读这张表要注意三点：

- **本地的封面全部加载失败（400）**，改动前后都一样：本机网络下 `cover.hetu-music.com` 解析到内网地址，生产构建的图片优化器拒绝内网地址（见 `next.config.ts`）。所以本地的 LCP 元素不是封面，而是卷首的歌曲数；I1、I2 的效果不在这张表里。封面请求的宽度已核对：改动前 828，改动后 640（Lighthouse 模拟 1.75 倍屏）。
- **LCP 的下降来自字体**：改动前，两千多 KB 的思源分片排在卷首文字之前；改动后，思源要等封面加载完或失败才开始下载，不再挡在前面。
- **「传输量」只算 Lighthouse 观察窗口里的部分**：改动后思源的分片在窗口末尾才开始下载，大部分没计入。思源最终仍会下载，总量没有变少，只是不再和首屏抢带宽。

上线之后要在线上首页按阶段 0 的同样条件重跑一次，那时封面能正常加载，才能看到 I1、I2 的效果。

### X3、X4：保留现状

- **X3**：点标志时的 `router.refresh()` 保留。最早点标志是整页刷新（`window.location.href`），#62 改播放器、让音乐跨页不停时，换成了「重置筛选 + 回到顶部 + `router.refresh()`」，保留「重新拿一次页面数据」的意思而不打断播放。代价只是重新下载一次页面数据流（gzip 约 27 KB），而且只在点标志时发生。
- **X4**：不预加载详情页，保持 `prefetch={false}`。

**验收**：

- 列表视图的缩略图下载的图片不超过 2 倍显示宽度：✓（64px 的位置取 128–256px）；
- 没有播放过的页面，加载的 JS 里不再有播放条的代码：✓；
- 首屏封面不再懒加载，第一张带 `fetchpriority="high"`：✓；
- 首屏封面加载完之前，不下载思源字体：✓；
- 本地 Lighthouse 手机模式 LCP：24.8 s → 10.0 s（见「本地对比」；线上待上线后重测）；
- 切换简繁后，搜索词、类型、年份和页码都保留：✓（类型和搜索词实测，年份、页码同在查询参数里）。

## 阶段 2：搜索内核

**解决**：为 S1–S4 和 F2 准备。只写纯函数和测试，**不接入页面**。

### 1. 归一化

匹配之前，搜索词和被搜的文本都做同一套归一化：

1. 去掉标点、空格和各类符号；
2. 全角转半角，拉丁字母转小写；
3. **繁体逐字转简体**，一个字只换成一个字，所以长度不变。

每段文本归一化时，同时记下「归一化后第 i 个字 → 原文第几个字」的位置表，高亮时用它把命中区间映射回原文。

逐字转换表由脚本从 opencc-js 的字典生成（`scripts/gen-t2s-table.ts` → `src/lib/search/t2s.json`，生成后提交），客户端只打包这张表，不打包 opencc-js。生成方法：取 `TSCharacters`（繁→简）里一个字对一个字的条目，再把 `TWVariantsRev`（台湾异体字→标准繁体）接到前面。

实现时生成脚本多做了两件事：本身就是简体字的台湾异体字不收（`TWVariantsRev` 里有「么→幺」，原型照搬了，会把简体的「什么」转成「什幺」）；链式的条目一直转到底（「薴→苧→苎」）。脚本检查「转出来的字不会再被转」，不满足就报错。最终 3009 个字，gzip 后 13.0 KB。

已知的局限：繁体版按词转换（opencc 的 `twp` 方案，比如「软件」→「軟體」），逐字转回去得到「软体」，所以在繁体页用简体输入「软件」搜不到。古风歌词里这类现代词汇很少。

`normalize()` 在阶段 3 也要用：地址栏里的人名存归一化后的简体。

### 2. 匹配与排序

一首歌按它**命中的最好那一档**排序，档位越靠前排得越前：

| 档 | 条件（都在归一化之后比较） |
|---|---|
| 1 | 题名完全相同 |
| 2 | 题名以搜索词开头 |
| 3 | 题名包含搜索词 |
| 4 | 人名完全相同：演唱、作词、作曲、编曲，以及别署 `creditAliases` |
| 5 | 人名包含搜索词 |
| 6 | 专辑包含搜索词 |
| 7 | 题名近似：差一个字（见下文「5. 题名近似」） |
| 8 | 歌词有一整句和搜索词完全相同 |
| 9 | 歌词有一句包含搜索词 |
| 10 | 兜底命中，只对歌词 |

- **档内排序**：歌词档按命中的句数从多到少，再按第一处命中的位置从前到后；其余情况保持曲库原有顺序（稳定排序）。
- **歌词各档都排在元数据各档之后**，所以歌词索引到达时只会在末尾追加结果（对应 S5）。
- **单字搜索**只匹配第 1 到第 6 档，不搜歌词，否则几乎每首歌都会命中。已确认接受：单字搜不到歌词。

### 3. 多个词

搜索词按空格分开时，每个词都要在这首歌的某个字段里命中（不必是同一个字段或同一句）。这首歌的档位，取各个词各自最好档位中**最差**的那一个。片段优先选同时包含多个词的句子。

### 4. 兜底：搜不到时再放宽

只在**精确命中一首都没有**、并且歌词数据已经就绪时启用（原定「少于 3 首」；评测里「明月如霜」题名完全命中 1 首，还会带出一句含「明月如」的别的歌，所以改成一首都没有才兜底，评测其余各条不受影响）：

1. 把归一化后的搜索词切成相邻两字的片段（bigram），比如「倾尽天夏」切成「倾尽」「尽天」「天夏」；
2. 逐句计算覆盖率：这一句包含了其中多少个片段；
3. 覆盖率达到阈值、并且至少命中 2 个片段的句子算兜底命中，每首歌取覆盖率最高的那一句。

阈值先定 0.6，用评测集调整。三个字的搜索词只有两个片段，错一个字就到不了阈值，这种情况接受搜不到。兜底结果在界面上要和精确命中区分开（阶段 5）。

### 5. 题名近似

去掉 Fuse 之后，题名打错字的容错由这一档负责，用编辑距离：

- **只用于题名**。人名只有两三个字，错一个字就是一半，带出的噪音比找回的多；专辑也不做。
- **搜索词（多个词时按单个词算）至少 4 个字，最多差 1 个字。** 错字、漏字、多字各算差一个字，相邻两字颠倒也算一个（Damerau 编辑距离）。
- **可以只对上题名的一段**，不要求从头到尾都对上（近似子串匹配）。比如「倾尽天夏」「倾尽天」都能搜到《倾尽天下》。
- **不看精确命中有几首，只看这个词在元数据上有没有对上。** 如果按「精确命中太少才启用」，歌词数据一到，精确命中数会变，题名近似的结果就会忽有忽无，已显示的结果又要重排（S5）。实现时加了一条：这个词在题名、人名、专辑上有任何一处精确命中（第 1–6 档），就不做近似，打对了题名就不会带出相近的题名（比如搜「雨碎江南」不会带出「烟雨江南」这类）。这个条件不看歌词，不影响 S5。这一档放在元数据各档的最后，保证「歌词档都在元数据档之后」不变。
- 在归一化之后比较，所以简繁互输照样适用。

已知的局限：三个字以内的题名打错字搜不到（比如「越人哥」），人名打错字也搜不到。

**不做拼音搜索，也不做同音匹配。** 讨论过两种：用 pinyin-match 支持全拼（`qingjin`）和首字母（`qjtx`）；把搜索词和题名、人名逐字转成拼音再比，用来容错同音的错字。都不做，因此不引入 pinyin-match，也不生成汉字转拼音的字表。旧方案本来也不支持拼音，评测集里的 4 条拼音用例在阶段 2 删掉。

### 6. 内存结构

#### 元数据

题名、人名、专辑各档用的数据，在搜索内核加载时建一次：

```ts
type SongMeta = {
  id: number;
  title: string;      // 以下都已归一化
  album: string;
  artist: string[];   // 人名按角色分开存，阶段 3 的筛选直接复用
  lyricist: string[];
  composer: string[];
  arranger: string[];
  aliases: string[];  // 别署 creditAliases
  genre: string[];    // 只供筛选，不参与搜索
};

function buildSongMeta(songs: Song[]): SongMeta[];
```

- **同一首歌只建一次。** 实现时改成用 `WeakMap` 按 `Song` 对象缓存，而不是按数组：曲库页先筛选再搜索，每次筛选得到新数组，但里面还是原来那些对象，照样复用。旧方案的 Fuse 在数据变化时要重建索引。360 首第一次建加搜索约 3 毫秒（台式机）。
- **人名按角色分开存**，不合成一个数组：搜索时各角色一起查，阶段 3 按角色筛选时各查各的。地址栏里存的人名、曲风也是归一化后的简体（F2），直接和这里的值比较，不用另写一套转换。
- **题名近似不建专门的索引。** 每次搜索把三百多个题名逐个算一遍编辑距离，估计不到 0.1 毫秒；题名都很短，近似子串匹配的计算量很小。
- 不保存原文：显示用的题名、人名直接从 `Song` 取。

歌曲数据本身不重新设计。首页内嵌的歌曲数据已经只取列表要用的字段（`SONG_LIST_VIEW_FIELDS`），360 首 gzip 后约 27 KB，为这一点改格式得不偿失。

#### 歌词

```ts
type LyricsCorpus = {
  corpus: string;          // 全部句子归一化后拼接，句间用 \u0001 隔开
  lineStart: Int32Array;   // 每句在 corpus 里的起点
  lineSong: Int32Array;    // 每句属于哪首歌（歌曲 id）
  lineIndex: Int32Array;   // 每句是那首歌的第几句（档内按第一处命中排序用）
  lines: string[];         // 原文，按句号索引，显示片段时用
};
```

- **分段构建，不一次做完。** 每处理四十首左右的歌就把主线程让出来一次（`scheduler.yield()`，不支持的浏览器用 `setTimeout(0)`），每段在手机上控制在十几毫秒以内。构建函数要能报告「部分就绪」，构建期间到来的搜索先只查元数据各档。如果手机上实测分段之后仍然明显，再把构建挪进 Web Worker。
- 每个搜索词只在 `corpus` 上反复调用 `indexOf`，再用二分查找定位到句子和歌，不遍历上万个短字符串，低端手机上省内存。
- 分隔符保证命中不会跨句；归一化去掉了所有符号，`\u0001` 不会出现在正文里。
- 位置表**按需计算**：只给当前页要显示片段的那十几句算。
- 兜底匹配也在 `corpus` 上做，只在精确命中太少时执行。

### 7. 片段

- 显示命中的那一整句，并给出高亮区间；
- 一首歌命中多句时，取最靠前的一句，并给出命中的总句数（界面上显示「等 N 处」）；
- 句子太长时以命中位置为中心截取，两头加省略号。

只有在歌词档命中的歌才给片段，和现在一致。

### 实测

用线上曲库（360 首，342 首有歌词，14716 句），台式机：

| 项目 | 结果 |
|---|---|
| 一次建好 `corpus` | 25 ms（页面上分段建，阶段 5 在手机上实测） |
| 第一次搜索（含建 `SongMeta`） | 3 ms |
| 之后每次搜索 | 0.2–0.9 ms（「七重纱衣 血溅了白沙」两个词加兜底最慢） |
| 搜索内核打包 | 压缩后 43 KB，gzip 18.6 KB，其中 `t2s` 表 13.0 KB |
| 繁体页歌词归一化后对不上简体原文 | 114 句（0.77%） |

对不上的都是按词转换造成的，最多的是「视频→視訊」「仿佛→彷彿」「苏醒→甦醒」「背→揹」。影响是：在繁体页用简体输入这些词搜不到，用繁体输入可以；简体页上用繁体输入这些词也搜不到。属于已接受的第 3 条。

### 实现时定下的细节

- 片段最长 32 个字（`SNIPPET_MAX_LENGTH`），阶段 5 接界面时按版面再定。
- 兜底命中的片段高亮对上的那些两字片段。
- 多个词都靠兜底时，片段取覆盖率最低的那个词所在的句子。
- `searchSongs` 在搜索框里没有可搜的字（空串、全是标点）时返回 `null`，调用方照常显示全部。

## 阶段 3：拆分 `MusicLibraryClient`，重构筛选

**解决**：C1、C2、C3、F1、F2、F4，以及讨论后的 F5、F6。搜索暂时仍用旧的 Fuse。

### 1. 拆分组件（C1）

卷首、工具栏、筛选面板、列表、分页各自成为组件；地址栏状态集中到一个 hook。拆分时要为阶段 4 留好位置：卷首、工具栏骨架和列表的第一页要能脱离地址栏状态单独渲染。

### 2. 用一份配置描述筛选维度（C2）

```ts
const FACETS = [
  { key: "genre",    param: "genre",    values: (s) => s.genre,    order: GENRE_ORDER },
  { key: "artist",   param: "artist",   values: (s) => s.artist },
  { key: "lyricist", param: "lyricist", values: (s) => s.lyricist },
  { key: "composer", param: "composer", values: (s) => s.composer },
```

地址栏状态、选项统计、匹配和筛选界面，都改成由这份配置驱动的通用实现。匹配时，曲风和人名各维度从阶段 2 的 `SongMeta` 取归一化后的值，和地址栏里的值比较（F2）；选项列表的显示和计数仍从 `Song` 取，按页面字形。同一维度内是「或」，维度之间是「且」，和现在一致。以后要加基调、意象母题这类筛选时，配置还要能表达「值本身有层级」（如母题属于某个分类），到时再扩展，现在不提前设计。

类型标签（`type`）是单选，年份是区间，这两个保持各自的写法，但同样从配置读取，不再单独散落。

### 3. 地址栏格式（F1、F2、F4）

- 年份存实际年份：`?year=2015-2020`；单独一年写 `?year=2018`；「未知」用 `&yearUnknown=1` 表示（F6 的讨论结果可能会改变这一条）。

## 阶段 4：服务端渲染默认状态，三档加载

**解决**：R1、R2（播放条之外的部分），并重新检查 X5、X6、I2。

### 1. 服务端渲染默认状态（R1）

推荐的做法：

- 首页保持 ISR。服务端把「第一页、不带任何筛选和搜索」的列表直接渲染成 HTML。
- 客户端**水合时不读地址栏参数**，先按默认状态渲染，保证和服务端的 HTML 一致；挂载之后，如果地址栏带了参数，再按参数筛选一次。
- 读参数的方式要换掉：只要水合时调用了 `useSearchParams`，整块就会退回客户端渲染。可以用 `useSyncExternalStore` 自己读 `window.location`，服务端快照返回默认值；写地址栏继续用 `history.replaceState`。
- 带参数的链接会先显示默认列表、再切到筛选结果。为了不闪，在 HTML 里放一小段内联脚本：检测到地址栏带了筛选或搜索参数时，先把列表区域隐藏，筛选完成后再显示。

卡片的进场动画是纯 CSS（`animate-in`），服务端渲染出来的卡片在 CSS 加载后就会播放，不用等水合。挂载后按地址栏参数重新筛选时，新的卡片再播一次，和现在「每次变化都播」的行为一致。代价是首屏卡片从透明开始，LCP 要等动画走完一部分才记到，会晚几百毫秒。和基线对比 LCP 时要把这一点考虑进去。

不推荐的做法：服务端读查询参数，按参数渲染。每个请求都要在服务端渲染一次，ISR 失效，服务器和数据库的压力明显上升。

### 2. 三档加载时机（R2）

「不在首屏路径上」不等于「等用户操作才加载」。延后的代码在页面空闲时就预加载好，用户第一次点搜索框或筛选按钮时，基本不需要再等：

| 档 | 什么时候加载 | 内容 |
|---|---|---|

## 阶段 5：接入新搜索

**解决**：S1–S5、R3。

### 1. 新接口 `lyrics-lines`

新增 `GET /api/public/songs/lyrics-lines?locale=&v=`，返回：

```ts
type LyricsLinesEntry = {
  id: number;
  lines: string[]; // 按页面字形，已去掉署名区与说明行
};
```

- **句子切分复用 `buildFolio`**（`utils-folio.ts`），传入歌名和 `lyricsStart`。它已经能去掉开头的「作词：」之类的署名区和说明行，切出来的句号也和详情页一致（阶段 7 用得上）。
- **繁体版在服务端逐句转换**（`toTraditional`，和详情页同一个转换器），保证句数不变。字形用 `localeFromRequest` 取（`src/lib/server/request-locale.ts`）。
- **用新路径，而不是改旧接口的格式。** 旧接口 `lyrics-index` 在 CDN、Service Worker（`NetworkFirst`，网络超过 5 秒或离线时返回旧缓存）和 ISR 三处都有缓存，原地改格式的话，部署后一段时间内客户端会拿到旧格式。
- 不带时间戳。以后要做「从这句开始听」，再加一个和 `lines` 等长的 `times` 数组。
- 下载格式不做专门设计：原型实测压缩后比旧接口还小。

### 2. 缓存：带版本号的地址

- 首页的服务端数据里算出一个歌词版本号：全部歌曲最近一次更新时间的短哈希，传给客户端。
- 客户端请求 `lyrics-lines?locale=…&v=<版本号>`。地址不变，数据就按「不会再变」缓存：响应头设长缓存（`immutable`）；`sw.ts` 为这个接口单独加一条 `CacheFirst` 规则，配 `ExpirationPlugin`（简繁各留两三个版本）。不放进现有的 `PUBLIC_CACHEABLE_API`，那条是 `NetworkFirst`。
- 歌词更新后版本号随之变化，客户端自然请求新地址。
- **接口忽略 `v`，始终返回当前数据。** 首页是 ISR 页面，带出去的版本号可能比接口实际的数据新或旧；`v` 只用来区分缓存地址，下一次版本号变化时自然纠正。也因此，`server-revalidate.ts` 不必为这个接口清 CDN 缓存。

### 3. 加载时机（三档里的第三档）

- 歌词索引在搜索框获得焦点时开始拉；地址栏里已带搜索词时，挂载后立即拉。不再固定延迟 1 秒（R3）。
- 不放进空闲预加载：数据比代码大得多（gzip 约 165 KB），而大多数访客不搜索。之后如果想更激进，可以在没开省流量模式（`navigator.connection.saveData`）时也空闲预加载。
- 从点进搜索框到敲完第一个词，通常已经过去半秒以上，再加上 300 毫秒的防抖，这段时间里题名、人名的结果先出来。
- 索引到达之前只匹配第 1 到第 7 档，结果末尾标一行「歌词检索准备中」；到达后分段构建 `corpus`，追加歌词各档的结果，已经显示的结果不重排（S5）。
- 第二次访问时，索引直接从 Service Worker 读出，「歌词检索准备中」只在第一次出现。

### 4. 接入页面

1. `src/hooks/library/useLyricsLines.ts` 取代 `useLyricsIndex`：按页面 locale 拉取，query key 带 locale 和版本号。
2. 曲库页把阶段 3 包好的搜索接口换成 `rank.ts`。
3. `GridCard`、`ListRow` 渲染高亮、「等 N 处」和兜底标记；繁体页显示繁体原文。样式按 DESIGN.md。
4. 补上「歌词检索准备中」的文案（简繁两份 messages）。

这次不做：同音字匹配；服务端全文检索；播放器歌词和反馈表单选歌在繁体页显示简体的问题（另起 PR）；搜索结果的界面改版。

**开工前要定**：

1. **兜底结果怎么标记**：片段前标「近似」，或者和精确命中之间加分隔，按 DESIGN.md 定。

**验收**：

- 繁体页上分别用繁体、简体输入同一句歌词，结果一致，片段显示繁体；
- 先输入搜索词、再等歌词索引到达：已显示的结果顺序不变，歌词命中的结果追加在后面；

- 中档手机上，歌词索引到达时正在输入，输入框不卡顿；

## 附录 A：问题清单

编号按类别：R 渲染，I 图片，T 字体，X 交互，F 筛选，S 搜索，C 代码结构。状态：**已确认**（按本文方案改）、**待讨论**（改之前先讨论）、**待验证**（要先在浏览器里确认）、**保留**（有意的设计，不改）。

### 渲染

- **R1 首页 HTML 里没有内容，用户先看到加载屏。**（待讨论 → 阶段 4）`MusicLibraryClient` 通过 nuqs 读地址栏参数，nuqs 内部用 `useSearchParams`；静态预渲染遇到它就退回最近的 Suspense 边界，HTML 里只剩 `<Loading />`。用户要等 JS 下载、执行、水合，再在客户端渲染出卡片，图片才开始下载。搜索引擎拿到的原始 HTML 也只有加载屏，Google 曾把卷首标语当作首页摘要，就是这个原因。
- **R2 首屏用不到的 JS 也一起加载。**（待讨论 → 阶段 1、4）Base UI 与 floating-ui 只在打开筛选下拉、顶栏菜单时才用到；播放条 `PlayerBar` 在全站的 `GlobalPlayer` 里静态引入，没有在播放也会被加载；Fuse 在挂载时就加载。framer-motion 保留，不在此列。
- **R3 挂载时就为搜索做准备，不管用户搜不搜。**（已确认 → 阶段 4、5）挂载时为整个曲库建 Fuse 索引；挂载 1 秒后无条件下载全量歌词，和首屏渲染抢主线程、和首屏封面抢带宽。大多数访客不搜索。Lighthouse 没有做任何搜索，页面加载时仍下载了 171 KB 的歌词索引。

### 图片

- **I1 封面下载的尺寸远大于显示尺寸。**（已确认 → 阶段 1）`CoverArt` 写的是 `width={400}`，没有 `sizes`，按 Next 默认的尺寸档位会请求 640 px（1 倍屏）或 828 px（2 倍屏）的图。网格卡片显示约 300 px；列表视图的缩略图只有约 56 px，下载的却是同一张图。
- **I2 首屏封面没有优先加载。**（已确认 → 阶段 1）所有封面都是懒加载，首屏那几张也要排队。Lighthouse 实测 LCP 元素就是第一张封面，带着 `loading="lazy"`，请求 828 px 宽的图，显示 364 px。
- **I3 封面经过自己服务器上的图片优化器。**（待讨论 → 未排期）占服务器 CPU，缓存只有 1 小时（`minimumCacheTTL: 3600`）。没有实测过服务器负载。

### 字体

- **T1 两套思源字体占了首页传输量的六成以上。**（已确认 → 阶段 1，采用做法 B）next/font 加载的思源宋体 19 个分片 1.40 MB、思源黑体 19 个分片 1.09 MB，慢速网络下和首屏封面抢带宽。详见阶段 1。

### 交互

- **X1 结果每变一次，卡片都重播进场动画。**（保留）每张卡片有 700 ms 的上滑淡入，依次错开 40 ms；搜索、筛选时新出现的卡片会播，翻页时整页重播。有意的设计。
- **X2 卷首的歌曲总数随筛选结果变化，每次变化都有动画。**（保留）有意的设计。
- **X3 点左上角标志会调用 `router.refresh()`，重新下载整页数据。**（保留）替代了早先的整页刷新，不打断播放；代价约 27 KB，只在点标志时发生。
- **X4 点卡片进详情页之前没有预加载。**（保留）歌名链接设了 `prefetch={false}`，卡片点击走 `router.push`。讨论后决定不预加载。
- **X5 从详情页返回时恢复滚动位置会闪一下。**（待讨论 → 阶段 4）内容先设为透明，等数据就绪、滚回原位再显示。
- **X6 搜索框每敲一个字都改写地址栏两次。**（待讨论 → 阶段 4）搜索词一次，页码重置为 1 又一次。外面还包了一层 `useSyncedQueryState` 和 nuqs 的状态互相同步。

### 筛选

- **F1 年份在地址栏里存的是滑块位置，不是年份。**（已确认 → 阶段 3）`?yearStart=2&yearEnd=5` 是年份列表里的序号。曲库一旦加入新年份的歌，所有序号错位，旧链接筛出来的是另一段年份。
- **F2 人名在地址栏里存的是当前页面的字形。**（已确认 → 阶段 3）繁体页的歌曲数据整套转成繁体（`toTraditionalSongList`），繁体页的链接发到简体页，名字对不上，筛选失效。反过来也一样。
- **F3 切换简繁会丢掉所有查询参数。**（已确认并修复 → 阶段 1）浏览器实测确认。原因：`useLocaleSwitch` 的 `switchTo` 调用 `router.replace(pathname, { locale })`，而 next-intl 的 `pathname` 不含查询参数。
- **F4 「全选」「反选」的压缩写法会随曲库变化改变含义。**（已确认 → 阶段 3）`encodeFilterParam` 在选中超过一半时只记录没选的项（`!某人`），全选记成 `*`。曲库新增一个人名后，旧链接会自动把他也包括进去。名字以 `!` 开头时还会被误读成排除项。
- **F5 选项不随其他筛选条件变化，容易组合出零结果。**（待讨论 → 阶段 3）可以把会导致零结果的选项置灰，不加计数。
- **F6 「未知」是年份滑轨的最后一格。**（待讨论 → 阶段 3）拖到最右端会把年份未知的歌也包含进来，界面上不容易看出来。

### 搜索

- **S1 模糊匹配的噪音太大。**（已确认 → 阶段 2、5）用 Fuse.js 做字符级模糊匹配（`threshold: 0.35`，`ignoreLocation: true`），散落的几个字也算命中。评测实测：「不知道」55 条结果里 52 条不含这三个字；题名搜索也有，「尽天下」39 条里 28 条不含、「越人歌」3 条里 2 条不含。
- **S2 排序难以解释，歌词索引一到结果还会重排。**（已确认 → 阶段 2、5）歌词和题名、人名在同一次 Fuse 打分里比，歌词权重 0.15，整首拼成长字符串又被按长度降权。没有歌词时用的索引（`createFuseInstance`：`threshold: 0.4`，专辑 0.2）和有歌词时用的（`useLyricsIndex`：`threshold: 0.35`，专辑 0.15）参数不同，索引一到，已显示的结果整体重排。
- **S3 片段展示粗糙。**（已确认 → 阶段 2、5）`processLyricsForSearch` 把各句用空格拼成一行，片段常常跨句截断；不高亮命中的字；片段里不一定有用户搜的字。
- **S4 繁体页搜不好、显示不对。**（已确认 → 阶段 2、5）歌词索引只有简体，题名、人名在繁体页上是繁体，搜索词不做简繁转换。长句里繁简不同的几个字会被模糊匹配吸收，所以能搜到；短的搜索词搜不到：评测里简体页输入「如夢」、繁体页输入「六軍不發」、简体页输入「鴉鬢簪花」都是 0 条结果。片段只显示简体。
- **S5 歌词索引到达会打断输入。**（已确认 → 阶段 5）挂载 1 秒后才拉全量歌词，用户已在打字时，结果会突然变一次。

### 代码结构

- **C1 `MusicLibraryClient` 有 621 行，整页都是客户端组件。**（已确认 → 阶段 3）状态、筛选的编码解码、工具栏、列表、分页都在一个文件里。不拆开，R1 就没法做。
- **C2 五个多选筛选的代码各复制了一遍。**（已确认 → 阶段 3）曲风、演唱、作词、作曲、编曲分散在 `useMusicLibraryState`、`MusicLibraryClient`、`searchAndFilterSongs`、`calculateFilterOptions`、`SongFilters` 五处。再加一个筛选维度要改五六个文件。
- **C3 搜索和筛选捆在一个 10 个参数的函数里。**（已确认 → 阶段 3）`searchAndFilterSongs` 和 `filterSongs` 按参数位置传值，后台的 `useSongs` 只用搜索，也要传一串空数组。
