# 曲库搜索重构实施方案

改曲库页（首页）的搜索之前读这份文档。范围是曲库页的搜索框，包括题名、人名、专辑和歌词全文；后台歌曲列表用的是同一套搜索函数，放在最后一个阶段一起换掉。

状态：待实施。标「待确认」的几处是默认方案，实施前定下来。

## 一、现在的问题

下面五条都已经确认，在线上是真实存在的。

1. **模糊匹配的噪音太大。** 歌词用 Fuse.js 做字符级模糊匹配（`threshold: 0.35`，`ignoreLocation: true`），散落的几个字也算命中。`useLyricsIndex.ts` 的注释里记着一个例子：搜「不知道」命中 53 首，其中 50 首根本不含这三个字。Fuse 的模糊匹配按编辑距离算，针对的是英文的拼写错误；中文记错歌词，通常是同音字，或者少记、多记几个字，编辑距离描述不了这两种情况。
2. **排序难以解释，索引一到结果还会重排。** 歌词和题名、人名在同一次 Fuse 打分里比，歌词权重只有 0.15，整首歌词又拼成一个长字符串，被 Fuse 按字段长度降权。一字不差地命中一句歌词，可能排在模糊沾到人名的歌后面。另外，没有歌词时用的索引（`utils-song.ts` 的 `createFuseInstance`：`threshold: 0.4`，专辑 0.2）和有歌词时用的索引（`useLyricsIndex.ts`：`threshold: 0.35`，专辑 0.15）参数不一样，歌词索引一到，已经显示的结果会整体重排。
3. **片段展示粗糙。** `processLyricsForSearch` 把各句用空格拼成一行，片段经常跨两句截断；片段不高亮命中的字；因为是模糊命中，片段里不一定有用户搜的那几个字。
4. **繁体页搜不好、显示不对。** 歌词索引只有简体，繁体页输入的繁体字不会转成简体，「夢」搜不到「梦」；片段也只显示简体。题名、人名在繁体页上是繁体（`getSongs(locale)` 已转换），反过来，用户输入简体又匹配不上。
5. **加载会打断输入。** 页面挂载 1 秒后才拉全量歌词。用户已经在打字的话，索引一到，结果列表会突然变一次（叠加第 2 条的重排）。

## 二、目标与不做的事

目标：

- 搜得到的都确实含有搜索词，搜不到时才放宽条件，并且放宽的结果排在后面。
- 排序规则写死、可以解释、可以测试。
- 片段显示命中的那一整句，高亮命中的字。
- 简繁两种页面都能用任意一种字形搜索，片段按页面字形显示。
- 歌词索引到达只会在末尾追加结果，不重排已经显示的结果。

这次不做：

- 同音字匹配（拼音只用于题名和人名，见第三节第 6 条）。
- 服务端全文检索（pg_trgm、pgroonga、Meilisearch）。以现在的曲库规模，客户端足够。
- 播放器歌词和反馈表单选歌在繁体页显示简体的问题。和这里同属「繁体页拿到简体」，但涉及的接口不同，另起 PR。
- 搜索结果的界面改版。第一版只改片段的内容和高亮，样式沿用现有的 `GridCard`、`ListRow`。

## 三、设计

### 1. 歌词索引：新接口，按句子存

新增 `GET /api/public/songs/lyrics-lines?locale=`，返回：

```ts
type LyricsLinesEntry = {
  id: number;
  lines: string[]; // 按页面字形，已去掉署名区与说明行
};
```

- **句子切分直接复用 `buildFolio`**（`utils-folio.ts`），传入歌名和 `lyricsStart`。它已经能去掉开头的「作词：」之类的署名区和说明行，切出来的句号也和详情页一致，以后做「点片段跳到那一句」（阶段 5）时不用再对齐。
- **繁体版在服务端逐句转换**（`toTraditional`，和详情页同一个转换器），保证句数不变。
- **用新路径，而不是改旧接口的格式。** 旧接口 `lyrics-index` 在三处有缓存：CDN（`PUBLIC_API_CACHE`）、Service Worker（`sw.ts` 的 `NetworkFirst`，网络超过 5 秒或离线时会返回旧缓存）和 ISR。原地改格式的话，部署后一段时间内客户端会拿到旧格式。新路径没有这个问题；旧接口保留一个版本，确认没有请求后再删。
- 不带时间戳。阶段 5 如果要做「从这句开始听」，再加一个和 `lines` 等长的 `times` 数组。

### 2. 归一化

匹配之前，搜索词和被搜的文本都做同一套归一化：

1. 去掉标点、空格和各类符号；
2. 全角转半角，拉丁字母转小写；
3. **繁体逐字转简体**，一个字只换成一个字，所以长度不变。

每段文本归一化时，同时记下一张「归一化后第 i 个字 → 原文第几个字」的位置表，高亮时用它把命中区间映射回原文。

逐字转换表由脚本从 opencc-js 的字典生成（`scripts/gen-t2s-table.ts` → `src/lib/search/t2s.json`，生成后提交），客户端只打包这张表，不打包 opencc-js。表的体积在阶段 0 量出来，预计几十 KB，gzip 后更小。

已知的局限：繁体版按词转换（opencc 的 `twp` 方案，比如「软件」→「軟體」），逐字转回去得到的是「软体」，所以在繁体页用简体输入「软件」搜不到。古风歌词里这类现代词汇很少，先不处理。

### 3. 匹配与排序

一首歌按它**命中的最好那一档**排序。档位越靠前，排得越前。档内的排序规则见表后。

| 档 | 条件（都在归一化之后比较） |
|---|---|
| 1 | 题名完全相同 |
| 2 | 题名以搜索词开头 |
| 3 | 题名包含搜索词 |
| 4 | 题名拼音命中（见第 6 条） |
| 5 | 人名完全相同：演唱、作词、作曲、编曲，以及别署 `creditAliases` |
| 6 | 人名包含搜索词，或人名拼音命中 |
| 7 | 专辑包含搜索词 |
| 8 | 歌词有一整句和搜索词完全相同 |
| 9 | 歌词有一句包含搜索词 |
| 10 | 兜底命中（见第 5 条），只对歌词 |

- **档内排序**：歌词档按命中的句数从多到少，再按第一处命中出现的位置从前到后；其余各档、以及前面这些都相同时，保持曲库原有的顺序（稳定排序）。
- **歌词各档都排在元数据各档之后。** 所以歌词索引到达时，只会在末尾追加新结果，不会打乱已经显示的那部分（对应问题 5）。
- **单字搜索**只匹配第 1 到第 7 档，不搜歌词，否则几乎每首歌都会命中。

### 4. 多个词

搜索词按空格分开时，每个词都要在这首歌的某个字段里命中（不一定是同一个字段，也不一定是同一句）。这首歌的档位，取各个词各自最好档位中**最差**的那一个。片段优先选同时包含多个词的句子。

### 5. 兜底：搜不到时再放宽

只在**精确命中的歌少于 3 首**、并且歌词索引已经到达时启用。

1. 把归一化后的搜索词切成相邻两字的片段（bigram），比如「倾尽天夏」切成「倾尽」「尽天」「天夏」；
2. 逐句计算覆盖率：这一句包含了其中多少个片段；
3. 覆盖率达到阈值、并且至少命中 2 个片段的句子算兜底命中。每首歌取覆盖率最高的那一句。

阈值先定 0.6，阶段 0 用评测集调整。这样能处理「少记一个字、多记一个字、记错一个字」。三个字的搜索词只有两个片段，错一个字就到不了阈值，这种情况接受搜不到。

兜底结果在界面上和精确命中区分开（比如片段前标「近似」），不和精确命中混在一起。具体样式按 DESIGN.md 定。

### 6. 拼音

新增依赖 **pinyin-match**，只用于题名、人名和别署：

- 只在搜索词全是拉丁字母、并且至少 2 个字母时启用，避免误伤英文题名和单个字母；
- 支持全拼（`qingjin`）和首字母（`qjtx`）；
- 对归一化后的文本做拼音匹配，返回的命中位置再经位置表映射回原文，用于高亮。

不用于歌词：歌词又长、同音字又多，噪音太大。

### 7. 片段

- 显示命中的那一整句，高亮命中的字（命中区间经位置表映射回原文）；
- 一首歌命中多句时，显示命中位置最靠前的一句，后面标「等 N 处」；
- 句子太长时，以命中位置为中心截取，两头加省略号；
- 繁体页显示繁体原文（接口按 locale 返回）。

只有在歌词档命中的歌才显示片段；在元数据档命中的歌不显示片段（和现在的行为一致）。

### 8. 加载时机

- 搜索框获得焦点时就开始拉索引；地址栏里已经带了搜索词（`useMusicLibraryState` 里的 `searchQuery`）时，页面一挂载就拉。不再固定延迟 1 秒。
- 索引到达之前，只匹配第 1 到第 7 档，结果列表末尾标一行「歌词检索准备中」；索引到达后追加歌词各档的结果。
- 归一化后的句子在索引到达时算一次，之后每次按键只做查找。防抖沿用现有的 300 毫秒。

### 9. 代码结构

搜索内核写成不依赖 React 的纯函数，单独测试：

```
src/lib/search/
  normalize.ts     归一化与位置表
  t2s.json         逐字繁转简表（脚本生成）
  pinyin.ts        对 pinyin-match 的封装
  rank.ts          分档匹配、多词、兜底、排序
  snippet.ts       片段截取与高亮区间
src/hooks/library/
  useLyricsLines.ts  拉取索引，构建归一化句子（取代 useLyricsIndex）
  useFilteredSongs.ts 改为调用 rank.ts
```

`searchAndFilterSongs` 里的筛选部分（类型、年份、人名、曲风）保持不变，只把搜索那一步换掉。

## 四、依赖变化

- 新增：`pinyin-match`。
- 删除：`fuse.js`（阶段 4 完成后）。
- `opencc-js` 仍然只在服务端用。

## 五、实施步骤

每个阶段可以单独上线。

### 阶段 0：评测集与原型

1. 整理评测集，放在 `src/lib/search/eval-cases.ts`，每条写明搜索词和应该搜到的歌（排在前几名）。至少要覆盖：
   - 完整题名、题名的一部分、题名首字母（如 `qjtx`）；
   - 人名、别署；
   - 歌词原句、歌词里的半句；
   - 记错一个字的歌词、少记一个字的歌词；
   - 繁体页上分别用繁体和简体输入；
   - 第一节提到的已知坏例子：「不知道」。
2. 写脚本 `scripts/search-eval.ts`，对同一份曲库数据分别跑旧方案（Fuse）和新方案，输出两边的前 10 名和命中率。
3. 量三个数：新接口的响应大小（原始与 gzip 后）、`t2s.json` 的大小、中档手机上单次搜索的耗时。单次搜索如果超过 16 毫秒，考虑放进 Web Worker。
4. 用评测结果确定兜底阈值和「少于 3 首才兜底」的这个 3。

### 阶段 1：搜索内核

实现 `src/lib/search/` 下的模块和 `t2s.json` 生成脚本，配单元测试：归一化与位置表、每一档的判定、多词、兜底、拼音、片段截取。评测集作为测试的一部分，防止以后改坏。

### 阶段 2：新接口与缓存链路

1. 新增 `lyrics-lines` 接口，用 `localeFromRequest` 取字形（见 `src/lib/server/request-locale.ts`），设 `revalidate` 和 `PUBLIC_API_CACHE`。
2. `server-revalidate.ts` 里 `refreshSongs` 和 `refreshPublicPages` 的路径列表加上新接口的两个字形：`/api/public/songs/lyrics-lines` 和 `?locale=zh-TW`（参照意象母题接口的写法）。
3. `sw.ts` 的 `PUBLIC_CACHEABLE_API` 加上新路径。这个正则只匹配路径部分，带 `?locale=` 的请求也能匹配上；Cache Storage 按完整 URL 存，简繁两份不会混。

### 阶段 3：接入曲库页

1. `useLyricsLines` 取代 `useLyricsIndex`：按页面 locale 拉取（`useLocale()`），query key 里带上 locale，按第三节第 8 条的时机拉取。
2. `useFilteredSongs` 改为调用 `rank.ts`；`MusicLibraryClient` 的 `getLyricsSnippet` 改为使用新的片段与高亮区间。
3. `GridCard` 和 `ListRow` 渲染高亮、「等 N 处」和兜底标记，样式按 DESIGN.md。
4. 补上「歌词检索准备中」的提示文案（简繁两份 messages）。

### 阶段 4：后台歌曲列表，删掉 Fuse

`useSongs`（后台 `SongListClient` 在用）改为调用 `rank.ts`，只用元数据各档。随后删除 `createFuseInstance`、旧的 `lyrics-index` 接口及其在 `sw.ts` 和 `server-revalidate.ts` 里的条目，并卸载 `fuse.js`。旧接口要在新版上线至少一个 CDN 缓存周期之后再删。

### 阶段 5（可选）：点片段跳到那一句

片段链接到详情页时带上句号，比如 `#lyrics-12`。`LyricsFolio` 滚动到那一句并短暂高亮。因为句子切分复用了 `buildFolio`，句号两边是一致的。之后还可以加「从这句开始听」，届时接口需要补上 `times`。

## 六、待确认

1. **去掉 Fuse 之后，题名、人名打错字就搜不到了。** 兜底只对歌词。如果希望人名也能容错，可以把兜底扩展到人名，但人名通常只有两三个字，切出来的片段太少，效果有限。默认方案：不做。
2. **兜底结果怎么标记。** 是否在片段前标「近似」，或者和精确命中之间加一条分隔，按 DESIGN.md 定。
3. **单字搜索不搜歌词**，这样是否可以接受。
4. **繁体页用简体输入「软件」这类现代词汇搜不到**（见第三节第 2 条），是否可以接受。

## 七、验收

- 评测集全部通过，新方案在评测集上的命中率不低于旧方案。
- 「不知道」只搜出确实含这三个字的歌；如果一首都没有，才出现兜底结果，并且有标记。
- 繁体页上分别用繁体、简体输入同一句歌词，结果一致，片段显示繁体。
- 先输入搜索词、再等歌词索引到达：已经显示的结果顺序不变，歌词命中的结果追加在后面。
- `qjtx` 能搜到《倾尽天下》。
- 单次搜索在中档手机上不超过 16 毫秒。
