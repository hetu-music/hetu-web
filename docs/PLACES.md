# 河图志：地点与打卡

「河图志」：歌里写到的地方，画在一张水系图上，读者可以记下自己到过哪里。改动地点数据、水系图或打卡之前读这份文档。

**状态：第一步的表已建（`20261119120000_places.sql`），初始数据已写成迁移（`20261119120100_places_seed.sql`），页面还没做。** 原型在 `/lab/map`（`src/components/lab/map/`），数据仍是写死的。正式路由是 `/places`。

用词：功能叫**河图志**（「河图」既是河的图，也是歌手的名字；「志」是地理志的志，也是记）；读者自己的记录叫**行迹**；卷首题词用《蒹葭》的「溯洄」，对应入场动画从河口逆流往上画。

## 一、做什么，不做什么

功能由三部分组成：

1. **地点与词句**：每处地点挂在写到它的那句歌词上（挑不出句子的挂整首歌，演出场馆不引歌词），画成水系图上的一站。
2. **到过**：读者记下自己到过哪些地方，连成自己的「行迹」。
3. **批注**：在地点下说的话，就是那句歌词下的批注（或整首歌的评论），直接复用详情页的评论。

刻意不做的：

| 不做 | 原因 |
|---|---|
| 底图加发光点的「点亮」 | 结构本身俗气。河是主体，地点是河上的站 |
| 进度条、百分比、徽章 | 打卡不是收集任务。统计只写一行字，比如「到过 7 处，沿着 3 条河」 |
| GPS 校验 | 打卡没有奖励，作弊没有好处；校验会让以前的行程补录不了，还有坐标偏移和隐私问题 |
| 照片（第一版） | 存储、审核和 EXIF 位置隐私都要另外处理，等前两部分跑起来再说 |
| 地图页单独的留言墙 | 和评论重复。见第五节 |

## 二、数据

和意象体系是同一个结构：`places` 相当于 `imagery`（独立的词表），`song_places` 相当于 `song_imagery`（挂在版本上的标注）。

```
places ─── song_places（挂在版本上，随发布）─── song_versions
   └────── place_visits（读者数据）─── users
```

```sql
places                                    -- 地点；不分版本，后台直接改，记审计
  id          bigint identity             -- 出现在地图页的地址里
  name        text not null               -- 图上的短名：「午门」
  full_name   text                        -- 全称，与短名相同时留空：「故宫博物院·午门」
  region      text not null               -- 「北京」「湖南 · 长沙」
  lat, lng    numeric                     -- WGS84，给「我在附近」用；可空
  created_at
  unique (name, region)

song_places                               -- 编校数据，开草稿时整份复制，发布时一起上线
  version_id  bigint references song_versions on delete cascade
  id          bigint identity             -- 各版本间不变
  place_id    bigint references places on delete restrict
  relation    text check (relation in ('setting', 'venue'))
                                          -- 歌里的地方 / 演出场馆
  anchor_index integer                    -- 第几句；挂整首歌时为空
  anchor_time  numeric(8,3)               -- 那一句的时间；纯文本歌词为空
  anchor_quote text                       -- 那一句的全文（toQuote），改词后按引文重定位
  note        text                        -- 「2016 年心时纪河图现场」
  created_at, created_by
  primary key (version_id, id)
  check ((anchor_index is null) = (anchor_quote is null))
  check (relation <> 'venue' or anchor_quote is null)
  unique nulls not distinct (version_id, place_id, relation, anchor_quote)

place_visits                              -- 读者数据，不审计
  user_id     uuid references users on delete cascade
  place_id    bigint references places on delete cascade
  visited_on  date                        -- 可空：记得去过，不记得哪天
  created_at
  primary key (user_id, place_id)
```

- **词句不存第二份。** 地图上显示的词句由 `anchor_quote` 去已发布版本的歌词里找，校记改了正文，地图跟着变。找不到的那一行不显示，后台在发布前标出来，和校记同样处理。
- **一处地点引了几句，就写几行**，每行一句。
- **关系只分两种。** 歌里的地方（`setting`）有代表句就挂句，用和校记、评论相同的行号、时间加引文定位；挑不出句子的挂整首歌，不填锚点。演出场馆（`venue`）不引歌词。
  - 起初分过「写到」（词里写出了地名）和「所指」（整首歌讲那里），但打卡表里十几处的代表句并没有写出地名（《宝塔镇河妖》《你好岳麓山》……），硬分就得丢掉整理者挑的句子。界面上该显示句子还是整首歌的评论，只看挂没挂句，用不着这个区分。
- `song_places` 是随发布的表，按 `DATABASE.md` 的要求做三件事：外键指 `song_versions`、加进 `ensure_draft` 的复制、补 `published_` 视图。另外挂上 `record_audit_log`。
- `place_visits` 一人一处一行。再去一次只改日期，不记多次到访（见第八节）。
- 写入走服务端接口（`/api/public/...`），用 service role；本人读自己的记录用自己的会话，经 RLS。迁移里显式写授权。
- **水系图的版式不进数据库。** 河的走向、每站的示意坐标、地名写在河的哪一边，都是手工排出来的，放在代码里，按 `places.id` 对应。还没排进图的地点，窄屏目录里照常显示，宽屏图上暂时没有。

## 三、地图页

宽屏是水系图加左栏，窄屏是从入海口往上读的目录，沿用原型的结构。这一页不受 `DESIGN.md` 约束。

选中一处地点，面板里依次是：

1. 地名、地区。
2. 每首歌一组：竖排的词句、歌名、备注。
   - 「从这句听」：有带时间的歌词、并且有播放权限时才出现，和详情页点句播放用同一套逻辑。
   - 点词句：跳到详情页的这一句（见第四节）。
3. 批注：取赞数最多的三条，加一个「全部 N 条」。点「全部」或「写一句」都跳到详情页。
   - 挂在句子上的，取这句下的批注，跳到详情页的这一句。
   - 挂在整首歌上的（包括演出场馆），取整首歌的评论（`anchor = 'song'`），跳到详情页的评论区。
4. 「到过」按钮，点了可以补填日期。
5. 「同一首歌还到过」：沿用原型。

另外两项：

- **我在附近**（窄屏顶部）：读一次定位，展开最近的一处。定位只用来找地点，不存，也不做校验。
- **我的行迹**：把自己到过的地点按日期连成一条线叠在河上，用原型里画同曲弧线的那种线。没填日期的只标出到过，不进连线。

## 四、详情页

- **旁注。** 宽屏下，挂了地点的那句在右侧旁注栏写出地名，地名前画一道短横，也就是地图上标地点的那一笔。点它打开地图并选中这一处。旁注与意象旁注并列，配色按详情页的 `--tone`，不借地图的河色和朱砂色。
- **歌词本身不加标记。** 歌词上已经有意象着重号和批注标记了。
- **窄屏。** 点一句展开的操作栏里，有地点的句子多一项「去这里」。
- **读者到过的地点**，旁注那道短横改用强调色。不另加徽章。
- **挂在整首歌上的地点与演出场馆** 没有对应的句子，在卷尾补遗附近用一行小字带过。
- **新的链接参数。** 详情页要支持 `?line=N`（滚到第 N 句并短暂高亮，用 `scrollToLine`）和 `&annotate`（同时打开这一句的批注框）。地图页跳过来都用这组参数。

## 五、打卡与评论

**不新建留言，也不给评论加「打卡」类型。** 在一处地点说的话，就是它挂的那句歌词下的一条普通批注；挂在整首歌上的地点（包括演出场馆），就是对整首歌的一条普通评论。

不单列类型的理由：

1. **边界说不清。** 到过的人写了一句对歌词的理解，算不算打卡？让用户发评论时自己分类，分不准，也没人在意分得准不准。
2. **想要的效果都能推出来。** 下面两项都由 `place_visits` 在读取时算出，不存（「能算的不存」）：
   - 作者到过这句挂的某处地方（整首歌的评论则看这首歌挂在整首歌上的地点），署名旁就加一个「到过」。只显示「到过」，不显示日期：日期只有本人看得到。
   - 地图面板里的批注，到过的人写的排在前面。
3. **改动面太大。** 加类型要改评论表的约束、批注框、详情页的渲染和后台的审核筛选。

推出来的标签有一点和单列类型不同：在去之前写的批注，去过之后也会带上「到过」。这没有问题，那个人确实去过。取消「到过」，标签也就跟着没了。

只想给自己看的话，评论本来就有 `visibility = 'private'`。
