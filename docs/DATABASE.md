# 数据库设计

本站数据库的目标结构、约定与迁移计划。新建表、改表结构、新增挂在别的数据上的表之前先读本文件。

本文写的是**目标**，不是现状（2026-11-15 定稿，尚未开始迁移）。现状以 `supabase/schema.sql` 为准：
歌曲仍在 `temp`（后台工作版本）与 `music`（线上快照）两张表里，各段迁移完成后在第九节打勾。
讨论中定下来的事项记在第十节。

## 一、原则

1. **身份与内容分开。** 歌有一张身份表，只回答「这是哪一首」；会变的内容放在版本里。读者数据指向身份，内容怎么改都不牵动它们。
2. **只存事实，能算的不存。** 存了就会与源头对不上，还得有人同步。确有理由要存的，写进第八节的缓存清单。
3. **状态由事实得出。** 「在线」「有未发布改动」「已下架」都从指针与版本算出，不另设状态列。
4. **规则尽量由结构保证。** 能用外键、唯一索引表达的，不靠约定和代码检查。
5. **审核以整首歌为单位。** 编校数据不分人写的、agent 写的，也不逐条确认：人审核一首歌就是审核它的全部，发布就是一起发布。agent 只写草稿，不能发布。
6. **公开端只读视图。** 「只看线上版本」这个条件写在视图里，不靠每处查询自己记得加。

## 二、全貌

```
歌 songs ─┬─ 版本 song_versions ─┬─ song_imagery     意象标注
          │   （资料）            ├─ song_emotions    基调
          │                      └─ song_collations  校记与补遗（+ 订者名单）
          ├─ song_links    各平台链接
          ├─ song_assets   封面、简谱
          ├─ song_audio    音频（原 navid_song）
          └─ 读者数据       comments · collections · user_requests · stream_grants

意象体系   imagery_categories（类别）─ motifs（母题）─ imagery_motifs ─ imagery（词）
基调词表   emotions
用户      users
署名      credit_aliases
独立内容   story_qjtx · quiz_results · audit_logs
```

挂在歌上的数据分两类：

|                                    | 挂在哪               | 随发布吗                           |
| ---------------------------------- | -------------------- | ---------------------------------- |
| 资料、意象标注、基调、校记与补遗   | 版本 `song_versions` | 随：在草稿上改，发布时一起上线     |
| 链接、封面与简谱、音频、读者数据   | 歌 `songs`           | 不随：属于这首歌本身，保存即生效   |

新增挂在歌上的表，先判断属于哪一类。随发布的要做三件事：外键指 `song_versions`、加进 `ensure_draft` 的复制、补 `published_` 视图。

## 三、歌曲与版本

### 表

```sql
songs
  id               bigint generated by default as identity primary key   -- 沿用现有 id
  live_version_id  bigint null          -- 线上版本；空 = 不在线上
  created_at, created_by
  foreign key (id, live_version_id) references song_versions (song_id, id)  -- 只能指向自己的版本

song_versions
  id               bigint generated always as identity primary key
  song_id          bigint not null references songs on delete cascade
  title, date, album, track, tracktotal, discnumber, disctotal,
  artist[], lyricist[], composer[], arranger[], albumartist[],
  genre[], type[], length, lyrics, lyrics_start, comment, dispute_note     -- 列名、类型不改
  published_at     timestamptz null     -- 空 = 草稿；非空 = 已冻结
  created_at, created_by, updated_at, updated_by
  unique (song_id, id)
  unique (song_id) where published_at is null    -- 每首歌至多一个草稿
```

- `song_versions` 是**一个版本一行**：草稿至多一行，保存就是覆盖它；每发布一次多一行冻结的版本。
- 历史版本全部保留，不参与任何读取，只备查。
- 冻结的版本及挂在它上面的编校数据，触发器拒绝修改与删除（删歌时的级联除外）。

### 状态

| 状态           | 判断                                   |
| -------------- | -------------------------------------- |
| 在线           | `live_version_id` 非空                 |
| 从未发布       | `live_version_id` 为空，且没有冻结版本 |
| 已下架         | `live_version_id` 为空，但有冻结版本   |
| 有未发布的改动 | 存在草稿                               |

### 生命周期

除「保存草稿」外都经数据库函数，函数里检查前置条件与权限，并写一条审计日志。

| 操作     | 做法                       | 前置条件                   | 结果                                                         | 谁能做         |
| -------- | -------------------------- | -------------------------- | ------------------------------------------------------------ | -------------- |
| 新建     | `create_song(资料)`        | —                          | 一首歌 + 它的草稿                                            | 管理员、agent  |
| 开草稿   | `ensure_draft(song_id)`    | —                          | 已有草稿就返回它；没有就复制最新冻结版本的资料与编校数据     | 管理员、agent  |
| 保存草稿 | 直接改草稿那一行           | `updated_at` 未变（乐观锁）| 覆盖草稿                                                     | 管理员、agent  |
| 放弃草稿 | `discard_draft(song_id)`   | 有冻结版本                 | 删掉草稿及其编校数据                                         | 管理员         |
| 发布     | `publish_song(song_id)`    | 有草稿                     | 草稿冻结，`live_version_id` 指向它                           | 管理员（人）   |
| 重新上线 | `publish_song(song_id)`    | 已下架且没有草稿           | `live_version_id` 指回最新的冻结版本                         | 管理员（人）   |
| 下架     | `unpublish_song(song_id)`  | 在线                       | `live_version_id` 置空；版本、草稿、读者数据都保留           | 超管           |
| 删除     | `delete_song(song_id)`     | 不在线                     | 歌及挂在上面的一切级联删除                                   | 超管           |

- 写编校数据的接口先调 `ensure_draft`，写在草稿上。只是打开看看不会开出草稿。
- agent 的账号角色是 `bot`（第六节）：能新建、开草稿、写草稿，不能发布。`publish_song` 等函数按 JWT 里的角色检查，不只靠接口层拦。

### 附属表

```sql
song_links                                -- 原 kugolink / qmlink / nelink
  song_id   bigint references songs on delete cascade
  platform  text check (platform in ('netease', 'qq', 'kugou'))
  url       text not null
  primary key (song_id, platform)
  unique (platform, url)                  -- 同一个链接不能挂在两首歌上

song_assets                               -- 封面、简谱是否已上传（文件在 R2）
  song_id   bigint references songs on delete cascade
  kind      text check (kind in ('cover', 'score'))   -- cover/{id}.jpg、nmn/{id}.png
  created_at, created_by
  primary key (song_id, kind)

song_audio                                -- 原 navid_song
  song_id   bigint primary key references songs on delete cascade
  navid_id  text unique not null
  suffix, duration, created_at
```

- `hascover`、`nmn_status`、`has_audio` 三列都不再存，由视图按 `song_assets`、`song_audio` 有没有对应的行算出。
  上传接口写 `song_assets`；触发器 `update_music_has_audio` 与音频同步里写 `has_audio` 的代码删掉。
- 这三张表不随版本，保存即生效：R2 里的文件是覆盖写的，跟着版本走的标记反而对不上文件；链接是这首歌本身的事实。
  agent 给已发布的歌补的链接因此不经审核就上线，这是接受的取舍。

### 视图

视图只是存起来的查询，不另存数据。一律写明列名，用 `security_invoker`。

| 视图                        | 内容                                                                              | 谁读                                 |
| --------------------------- | --------------------------------------------------------------------------------- | ------------------------------------ |
| `published_songs`           | 在线的歌 + 线上版本的资料 + `hascover` / `nmn_status` / `has_audio` + 三个链接列  | 公开端                               |
| `catalog`                   | `published_songs` 去掉 `dispute_note` 非空的（取代 `music_catalog`）              | 统计、推荐、寻曲、意象索引、登录画廊 |
| `published_song_imagery`    | 线上版本的意象标注，带 `song_id`                                                  | 公开端                               |
| `published_song_emotions`   | 线上版本的基调，带 `song_id`                                                      | 公开端                               |
| `published_song_collations` | 线上版本的校记与补遗，带 `song_id`                                                | 公开端                               |
| `working_songs`             | 每首歌的工作版本（有草稿用草稿，否则用最新冻结版本）+ 版本 id + 是否在线、有无草稿 | 后台、agent                          |
| `working_song_imagery`      | 工作版本的意象标注，带 `song_id`                                                  | 后台意象库的跨歌查询                 |
| `imagery_summary_all`       | 全部词及次数，按工作版本统计（已有，改定义）                                      | 后台词典                             |

- `published_songs` 的列名与现在的 `music` 一致，公开端代码基本只换表名。
- 后台按单首歌读基调、校记时，从 `working_songs` 拿到版本 id 直接查表，不另设视图。
- 函数 `imagery_occurrence_counts` 同样改为按工作版本统计，否则草稿与线上版会重复计数。

## 四、编校数据

三张表都挂在版本上，开草稿时整份复制，发布时一起上线。争议歌曲照常标注，汇总时由 `catalog` 排除。

```sql
song_imagery                              -- 原 imagery_occurrences
  version_id  bigint references song_versions on delete cascade
  imagery_id  bigint references imagery on delete cascade
  motif_id    bigint references motifs
  created_at, created_by
  primary key (version_id, imagery_id, motif_id)

song_emotions
  version_id, emotion_id, rank, created_at, created_by       -- 去掉 source
  primary key (version_id, emotion_id);  unique (version_id, rank)

song_collations                           -- song_id 改为 version_id，其余列不变
song_collation_revisers                   -- 不变，跟着校记一起复制
```

- **时间标签不存，读时在服务端算。** 标签就是「词在本曲字面出现的那几行」（`IMAGERY.md` 第三节），由 `songTimetags` 按同一版本的歌词算出，
  返回给前端的数据里仍叫 `lyric_timetag`。`syncSongTimetags`、`resyncSongTimetags`、发布后重算的那一步都删掉。
- **「同时算进」不存，读时展开。** 一条标注挂在词的 `primary` 母题上时，它的 `part` 各母题由 `imagery_motifs` 决定。
  `addParts` 补写的行，以及改词、改母题、删除时的连带维护都删掉。
- 草稿里改了歌词，后台按引文核对校记、按字面核对标注，标出对不上的，发布前处理。
- 评点（`comments`）挂在歌上，锚点照旧按行号 + 引文重定位，不记版本。

## 五、意象体系

母题从分类树里拆出来，「标注只能挂在母题上」由外键保证，不再靠 `level = 3` 的约定。

```sql
imagery_categories                        -- 只剩十七个类别
  id, name unique, description, created_at
  domain  text check (domain in ('自然', '人文', '情志'))     -- 门类；去掉 parent_id、level

motifs                                    -- 原分类树第三级，id 沿用（/imagery/[id] 的地址不变）
  id, name unique, created_at
  category_id  bigint not null references imagery_categories
  description  text not null

imagery                                   -- 词，不变
imagery_motifs                            -- category_id 改名 motif_id，指向 motifs；其余不变
```

门类改成一列后，原来的三行门类不再存在。代码里门类只按名字用（配色顺序、后台类别栏的行首、分类路径），
id 只在一次请求内当作 Map 的键，不进地址、不落库，说明也没有地方显示，所以不需要保留成表。
涉及的代码：`palette.ts` 的 `sortLevel1Categories`、`service-imagery-cloud.ts` 与 `service-song-imagery.ts` 的 `pathOf`、
`MotifsClient.tsx` 的类别栏、`word-motifs.ts` 的 `categoryPath`、`quiz/pool.ts` 与 `quiz/coverage.ts`。

## 六、用户与互动

| 表              | 改动                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| `users`         | `is_admin`、`is_super` 合成 `role`：`user / bot / admin / super`；同步到 JWT 的 `app_metadata.role`，RLS 与 `withAuth` 改读它 |
| `comments`      | `status`、`visibility` 由数字改为文本：`normal / pending / hidden / deleted`、`public / private`       |
| `collections`   | 去掉 uuid 主键，主键改为 `(user_id, song_id)`                                                          |
| `stream_grants` | `song_id` 改 `bigint`，加外键指 `songs`                                                                |
| 用户外键        | `collections`、`user_requests`、`quiz_results` 的 `user_id` 由 `auth.users` 改指 `public.users`        |
| `user_requests` | `varchar` 改 `text`，其余不变                                                                          |
| `quiz_results`  | 不变；`song_ids` 是测试结果的快照，不加外键，表注释里写明                                              |

读者数据挂在 `songs` 上，歌没上线或下架后数据仍在。公开端读写它们时经 `published_songs` 确认歌在线。

`role` 的四个值逐级包含：`bot` 能做后台的读写但不能发布、下架、删除，也不处理用户请求；`admin` 再加发布与放弃草稿；`super` 再加下架、删除与用户管理。
改 `role` 后旧的登录令牌里没有新字段，上线后管理员需要重新登录一次。

`story_qjtx`、`emotions`、`credit_aliases`、`comment_likes` 不变。

## 八、约定

**主键。** 实体用 `bigint` identity；关系表用自然的复合主键，不另加代理键；`users` 跟 `auth.users` 用 uuid；出现在分享链接里的用短文本 id。

**枚举。** `text` + `check`。代码值用英文小写；领域词汇本身是中文的（门类、基调的明暗扬抑）照用中文。不用数字代码，不用 enum 类型。

**时间戳。** 每张表有 `created_at`；行会被修改且有人读修改时间的才加 `updated_at`，由触发器维护。

**外键。** 引用必有外键，类型与被引用的列一致。例外只有快照，在表注释里写明。

**权限。**

- 新表、新函数在 migration 里显式授权。`anon`、`authenticated` 在表上的默认权限收回（函数的已在 `20261113130000` 收回）。
- 公开端：服务端用 service role 读视图。
- 后台与 agent：用本人的 JWT，经 RLS；生命周期函数是 `SECURITY DEFINER`，函数里按 JWT 的角色检查。
- 普通用户的写入：经服务端接口，用 service role。

**审计。** `record_audit_log` 触发器挂在：草稿的保存、三张编校表、意象体系四张表、`emotions`、`credit_aliases`。
`ensure_draft` 的整份复制不记（函数里设会话标记，触发器跳过）。生命周期操作由函数各记一条。读者数据不审计。日志保留 90 天。

**缓存清单**（存了派生数据的地方）：

| 存在哪里                | 由什么算出             | 谁维护                            |
| ----------------------- | ---------------------- | --------------------------------- |
| `comments.like_count`   | `comment_likes` 的行数 | 触发器 `comment_likes_sync_count` |
| JWT `app_metadata.role` | `users.role`           | 触发器 `sync_user_claims_to_auth` |

## 九、迁移计划

上线前备份数据库；回填的 migration 在末尾用断言核对行数，对不上就整体回滚。相邻两段可以合并成一次停机。
